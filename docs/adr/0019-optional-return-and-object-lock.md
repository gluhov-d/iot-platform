# ADR-0019: Необязательная часть — возврат объекта в топик и Object Lock

**Статус**: предложено, 2026-11-21 (на проверке дизайна); дополнено 2026-11-26 по ревью PR #7 (ILM удаляет прежние версии и пометки удаления; заголовки при возврате — списком) · **Спецификация**: [specs/002-failed-events](../../specs/002-failed-events/spec.md)

## Контекст

В задании три необязательных пункта: команда точечного возврата одного объекта в исходный топик; каскад из двух обработчиков; версии объектов и запрет удаления для бакета необработанных сообщений. Нужно решить, какие пункты берём, и как они связаны с основной частью.

## Решение

- Берём (1): команда возврата одного объекта в исходный топик. Команда читает JSON объекта, восстанавливает `key`, `value` и `headers` из base64 в исходные байты и публикует их в `sourceTopic` без пересериализации. `traceId` сохраняется, к сообщению добавляется заголовок-пометка о возврате (имя заголовка — в tasks.md).
- Берём (3): версии объектов и Object Lock бакета `failed-events` в режиме GOVERNANCE с default retention 180 суток, совпадающим с ILM.
- Lock задаётся только при создании бакета: включить его на существующем бакете нельзя (409 InvalidBucketState, см. research.md R12). Поэтому `failed-events` создаётся с `--with-lock` в основной части стенда. На уже созданном бакете без lock init падает с понятным сообщением, а не молча.
- ILM бакета с версиями (дополнено 2026-11-26): `Expiration.Days` на версионном бакете только ставит пометку удаления — прежняя версия JSON
  остаётся, и объём растёт после обещанных 180 суток. Поэтому правило `failed-events` содержит ещё `NoncurrentVersionExpiration`
  (`MINIO_EXPIRE_FAILED_EVENTS_NONCURRENT_DAYS` = 1 сутки после того, как версия стала прежней), а отдельное правило —
  `ExpiredObjectDeleteMarker` (вместе с `Days` в одном `Expiration` MinIO его не принимает). Версию под действующей блокировкой MinIO
  не удаляет и пробует на следующем проходе сканера. `ExpiredObjectAllVersions` и `DelMarkerExpiration` на бакете с lock MinIO запрещает
  (research.md R27).
- Версионирование включено, как требует lock. Условный PUT версию не создаёт (см. research.md R5), поэтому версии появляются только при явной перезаписи или удалении.
- Не берём (2): каскад из двух обработчиков. Он меняет сборщики сверх задания; второй потребитель той же темы — отдельная группа: она даёт двойную обработку и нагрузку на MinIO. Второго объекта нет — ключ и условная запись (ADR-0014).
- Реализация возврата и Object Lock — необязательная фаза P9 в tasks.md: пункты раздела «Дополнительно» задания, в обязательный минимум и в
  результат converge по основной части не входят; выполняется после неё.

## Последствия

- Lock GOVERNANCE: удалить объект до истечения срока можно только с правом bypass. Режим COMPLIANCE не выбран: его нельзя снять до срока; его поведение не проверялось.
- Истечение срока ILM под lock не проверено: 180 суток ждать нельзя. Срок ILM и срок lock совпадают (180 суток).
- Возврат публикует сообщение снова: оно пройдёт обработку заново, и ошибка повторится, если её причина не устранена. Это ответственность оператора.
- Повторный возврат того же объекта даёт второе сообщение в топике. Защиты от этого нет; поведение при обработке дубля не проверено.
- Возврат не удаляет объект из MinIO. Объект остаётся архивом, пока не истечёт срок.
- Версии и lock не влияют на запись процессора: условный PUT остаётся идемпотентным (ADR-0014).
- Возврат точечный: одна команда — один объект, массового возврата в объём этого ADR нет. Пачку объектов одного дня можно вернуть, повторив команду по списку ключей (ключи — ADR-0014): список дня — по префиксу `yyyy/MM/dd/`, отбор по коду ошибки — по `x-amz-meta-error-code` или полю JSON, префикса с кодом в ключе нет.
- Заголовки возвращаются в исходном порядке, с повторяющимися именами и значениями `null` (массив `headers` объекта `schemaVersion: 2`, ADR-0013);
  объекты `schemaVersion: 1` (заголовки объектом) команда тоже возвращает — в них повторов и `null` уже нет.
- Пометка о возврате меняет заголовки, но не байты `key` и `value`. Проверки байт в тестах возврата сравнивают именно `key` и `value`.
- Сборщики и процессор при этом не меняются: возврат — отдельная команда стенда.
- Реализация возврата (`make failed-replay`): `Replay.java` публикует байты из объекта через `kafka-clients` и Jackson. Консольный продюсер Kafka
  не годится: он читает строки, и байт `0x0a` в значении ломает сообщение; `kcat` в образах нет. В образе Kafka только JRE (нет `jdk.compiler`), поэтому
  `replay-tool.sh` запускает файл одноразовым контейнером с тем же JDK, что собирает сервисы, в сети стенда, а jar клиентов копирует из контейнера
  `kafka` (те же версии). Проверено `make failed-replay-test`: `key` и `value` с байтами `0x00`, `0x0a`, `0xff`, заголовки и `traceparent` совпадают побайтно,
  у каждого сообщения `x-replayed-from` = ключ объекта; неизвестный ключ — код 2, нечитаемая запись — код 3.
- Реализация Object Lock (`minio-init`): режим GOVERNANCE на `FAILED_EVENTS_LOCK_DAYS` суток по умолчанию задаётся S3-запросом `PUT ?object-lock`. Команды
  `mc retention` в сборке `pgsty/mc` работают с объектами и режима по умолчанию не имеют, а `mc retention info --default` пишет «Object locking is not
  enabled» даже на бакете с lock. `make minio-check` проверяет правило и поведение: учётка процессора не удаляет версию (нет права), администратор без
  обхода режима получает отказ (`WORM protected`), с `mc rm --bypass` удаляет.
- Срок ILM и срок блокировки равны (180 суток) и отсчитываются от создания версии. На 180-е сутки ILM ставит пометку удаления (блокировка
  этого не запрещает: данные версии не трогаются), через `MINIO_EXPIRE_FAILED_EVENTS_NONCURRENT_DAYS` суток удаляет прежнюю версию (блокировка
  к этому моменту истекла), затем — оставшуюся пометку. Объект хранится 181–182 суток. Прежняя запись «ILM удаляет версию, когда блокировка
  истекла» была неверной (R21). Поведение проверяется разовым прогоном на одноразовом MinIO со сроками в 1 сутки: после срока объекта нет
  ни в обычном списке, ни среди версий (research.md R27).
- Режим защищает только объекты, записанные после включения правила: объекты стенда, лежавшие до него, остаются без защиты.
- Проверочные объекты `make minio-check` и `make failed-replay-test` тоже под блокировкой; тесты убирают их удалением версии с обходом режима (учётка root).
  Объекты `make fep-quick-check` остаются до срока, как и раньше.

## Рассмотренные варианты

- Каскад из двух обработчиков: отвергнуто (см. Решение).
- Версии без Object Lock: не запрещают удаление. Отвергнуто.
- Object Lock в режиме COMPLIANCE: нельзя откатить до срока, проверено не было. Отвергнуто.
- Возврат через ручной producer по JSON: пересериализация меняет байты. Отвергнуто.
- Возврат через сборщик (повторное чтение объектов сервисом): связывает команду с сервисом-источником и меняет его код. Отвергнуто.
