# ADR-0001: Запись через Kafka, единственный писатель реестра

**Статус**: предложено, 2026-11-11 · **Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

Реестром устройств владеет device-collector-service: он пишет шарды через ShardingSphere-Proxy, получая изменения
из темы `devices`. Администратору нужны создание, изменение и удаление. Второй писатель в ту же базу вернул бы
блокировки между сервисами и потерянные обновления; своя база у device-service — второй источник истины;
синхронный вызов device-collector-service смешал бы в нём два потока изменений.

## Решение

device-service в базу не пишет. Он проверяет запрос и публикует `DeviceInfo` с `operation` в тему `devices` с
ключом `deviceId` (`acks=all`, идемпотентный продюсер) и отвечает `202 Accepted` с `Location` только после
подтверждения Kafka. Нет подтверждения за `DEVICE_COMMAND_SEND_TIMEOUT` — `503 COMMAND_NOT_ACCEPTED`. Применяет
команду device-collector-service — так же, как события роутера: по одному сообщению, идемпотентно, в одной
транзакции на шарде.

## Последствия

- Одна операция с побочным эффектом — двойной записи нет, outbox не нужен.
- Согласованность в конечном счёте: сразу после `202` GET может вернуть старые данные; клиент перечитывает позже.
- Предварительные проверки (`404`, `409`) — по отстающей модели чтения; окончательно решает владелец, отказ виден
  исходом `IGNORED` в журнале и метриках, а не ответом клиенту.

## Рассмотренные варианты

Прямая запись в шарды (два писателя), своя база + CDC (два источника истины), REST-вызов device-collector-service
(синхронная связь, два потока изменений в одном сервисе).
