# ADR-0016: Mimir вместо Prometheus; Loki и Tempo хранят данные в MinIO

**Статус**: предложено, 2026-11-21 (на проверке дизайна) · **Спецификация**: [specs/002-failed-events](../../specs/002-failed-events/spec.md)

## Контекст

Prometheus хранит метрики на локальном диске и не пишет в объектное хранилище. Задание требует Mimir как хранилище метрик и MinIO как хранилище для Mimir, Loki и Tempo. ADR-0012 уже перенёс сбор метрик сервисов в Alloy, который передаёт их через remote write. Алертов в Prometheus не было.

## Решение

- Prometheus удаляется: сервис, конфигурация и том.
- Alloy отправляет метрики через `prometheus.remote_write` в `http://mimir:8080/api/v1/push`. Экспортеры PostgreSQL и Kafka, Proxy, Keycloak и MinIO Alloy также скрейпит; в этом ADR меняется только приёмник.
- Mimir `grafana/mimir:3.2.6`, монолит `-target=all`, HTTP-порт 8080 (значение по умолчанию), `multitenancy_enabled: false`.
- Хранилище blocks: бакет `mimir-blocks`, префикс `blocks/`; ruler — префикс `ruler/` в том же бакете. Проверено на прототипе (см. research.md R13): префиксы работают. Объекты в корне бакета Mimir принимает за тенанта, поэтому без префикса нельзя.
- Retention: `limits.compactor_blocks_retention_period: 365d`; срок бакета 380 суток (ADR-0015).
- Grafana: источник с прежним uid `prometheus`, тип prometheus, URL `http://mimir:8080/prometheus`. Запрос `up` через Grafana прошёл (см. research.md R13), поэтому существующие дашборды не меняются.
- Loki 3.1.1 и Tempo 2.6.0 хранят чанки и блоки в `loki-chunks` и `tempo-traces`. Локальные тома остаются как WAL. Loki: `flush_on_shutdown` в 3.1.1 отсутствует (см. research.md R14), сбор файлов в Alloy идёт через `local.file_match` (см. research.md R14). Tempo на S3 работает (см. research.md R15).
- Alertmanager не включается: алертов не было, `-target=all` его не содержит. При `-target=all` API alertmanager отвечает 404; это проверено на прототипе при включённом `alertmanager` (см. research.md R13).
- Healthcheck для Mimir невозможен: в образе нет shell, curl и wget. Зависимые сервисы ждут `service_started`; скрипты проверок опрашивают `/ready` снаружи. Первые ~20 секунд после старта `/ready` отвечает 503 (см. research.md R13).

## Последствия

- Логи, трассы и метрики сервисов идут одним агентом Alloy (продолжение ADR-0012).
- Mimir в монолите — одна точка отказа для метрик. На стенде это приемлемо; масштабирование не проверялось.
- Mimir без healthcheck: состояние видно только снаружи, в compose его не отследить.
- Срок в Mimir (365 суток) меньше срока бакета (380): система удаляет первой, бакет страхует от ошибки конфигурации.
- Фактическое удаление по сроку не наблюдалось: сроки в прототипе не ждали (не проверено).
- Блоки Mimir без принудительного flush появляются по `block_ranges_period` (2 часа по умолчанию); время до появления без flush не измерено.
- Ruler и отдельные алерты Mimir в объём не входят.

## Рассмотренные варианты

- Оставить Prometheus с локальным хранением: не выполняет требование задания. Отвергнуто.
- Отдельные бакеты для ruler и alertmanager Mimir: не проверялось; префиксы в том же бакете работают (см. research.md R13). Отвергнуто.
- Mimir по микросервисам: для стенда избыточно. Отвергнуто.
- Loki и Tempo на локальном диске: задание требует MinIO. Отвергнуто.
