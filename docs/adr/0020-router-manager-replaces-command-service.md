# ADR-0020: router-manager вместо планового Command Service

**Статус**: предложено, 2026-11-28 (на проверке дизайна). Спецификация — [specs/003-router-manager](../../specs/003-router-manager/spec.md).

## Контекст

На контейнерной схеме с первой части платформы нарисован плановый Command Service (Spring Boot): хранит команду в PostgreSQL,
доставляет её устройству через Device Gateway (REST → MQTT/HTTP), подтверждение получает из темы `events`, тайм-аут ведёт
Camunda. Задание этой части вводит router-manager с другой моделью: роутер сам опрашивает сервис по gRPC и сообщает результат,
зависшие команды переводит механизм самого сервиса, администратор (дальше — API-оркестратор) вызывает сервис напрямую.

## Решение

- Узел Command Service заменяется на router-manager (Go). Маршрут команд: API-оркестратор → router-manager (gRPC, сервисный
  токен Keycloak); роутер ↔ router-manager (gRPC: опрос и результат).
- Связи Camunda и Device Gateway с командами (C1–C7 и E5 прежней схемы: запуск процесса команды, шаг «отправить», доставка, ack, тайм-аут) удаляются; сами узлы остаются как план: Camunda —
  для процессов оркестратора, Device Gateway — для телеметрии устройств.
- Статусы — из задания: NEW → SENT → SUCCESS | FAILED (вместо DONE).

## Рассмотренные варианты

- Camunda в цепочке (процесс создаёт команду и опрашивает статус): дублирует проход зависших и добавляет зависимость, которой
  задание не требует; можно добавить в части оркестратора, контракт это позволяет.
- Роутеры через Device Gateway: лишний шаг без пользы для gRPC-клиентов; задание показывает прямой вызов.

## Последствия

- Контейнерная и контекстная схемы перерисованы; таблица `device_commands` прежней подписи узла PostgreSQL заменена базой `iot_commands`.
- Прочие устройства (не роутеры) команд в этой части не получают.
