# ADR-0014: Ключ объекта в MinIO и идемпотентная запись

**Статус**: предложено, 2026-11-21 (на проверке дизайна); изменено 2026-11-22 по ревью PR #6 (единый ключ для читаемой и нечитаемой записи) · **Спецификация**: [specs/002-failed-events](../../specs/002-failed-events/spec.md)

## Контекст

Процессор пишет по одному объекту на каждое сообщение `failed-events`. Повторная доставка неизбежна: сбой после отправки и до подтверждения смещения, перебалансировка группы.

Первая редакция строила ключ читаемой записи из координат исходного сообщения (`sourceService/…/errorCode/sourceTopic-p-o`), а нечитаемой — из координат записи в `failed-events` (`unreadable/…`). Ревью показало дефект. Если схема сначала не найдена, объект записан в `unreadable/`, а процесс упал до подтверждения смещения, после восстановления схемы запись разберётся и уйдёт в обычную ветку. Ключ другой, `If-None-Match` не сработает, и на одну запись `failed-events` будет два объекта. У нечитаемой записи координат исходного сообщения нет, поэтому общий ключ можно построить только из координат самой записи `failed-events`.

Поиск нужен через полгода: по сервису, коду, дню, трассе и устройству.

## Решение

- Ключ объекта один для обеих веток: `<yyyy>/<MM>/<dd>/failed-events-<partition>-<offset>.json`. `partition` и `offset` — раздел и смещение записи в `failed-events`, дата — время этой записи (`timestamp`) в UTC. Эти три значения при повторной доставке записи не меняются, поэтому ключ тот же.
- Читаемая и нечитаемая запись различаются телом, а не ключом: у нечитаемой поле `kind = unreadable` в теле и метаданные `x-amz-meta-kind: unreadable` (правило — ADR-0018).
- Время записи — `timestamp` записи Kafka (по умолчанию `CreateTime`, его ставит продюсер сборщика при отправке). Оно не зависит от числа доставок записи процессору. Что тема использует `CreateTime`, а не `LogAppendTime`, проверяет тест ключа (T035); для `LogAppendTime` время тоже одно на запись.
- Тело JSON содержит все поля `FailedEvent`. `key`, `value` и значения `headers` — base64 от исходных байтов; `headers` с `schemaVersion: 2` (ревью PR #7) — массив `[{name, value}]` в исходном порядке, с повторами и `null` (ADR-0013). Времена — ISO-8601 UTC. Координаты исходного сообщения (`sourceTopic`, `sourcePartition`, `sourceOffset`) лежат в теле.
- Запись в объект: `PutObject` с `If-None-Match: *`. Ответ 412 означает, что объект уже записан; сообщение считается обработанным и смещение подтверждается. Версия не создаётся (см. research.md R5: `bitnamilegacy/minio` и `pgsty/minio`).
- HEAD с последующим PUT не используется: между двумя экземплярами процессора это гонка.
- Содержимое при повторе не сравнивается: 412 означает «объект с таким ключом уже есть». Ключ однозначно задаёт запись `failed-events`, поэтому сравнение не нужно.
- Метаданные объекта: `x-amz-meta-error-code`, `x-amz-meta-source-service`, `x-amz-meta-source-topic`, `x-amz-meta-device-id` (если есть), `x-amz-meta-trace-id` (если есть); у нечитаемой записи только `x-amz-meta-kind: unreadable`.
- Поиск через полгода: `ListObjectsV2` по префиксу дня (`yyyy/MM/dd/`); сервис, код, `traceId` и `deviceId` — по метаданным объекта (`mc find --metadata`) или полю JSON.

## Последствия

- Одна запись `failed-events` даёт ровно один объект в обеих ветках, в том числе при сбое между записью `unreadable` и подтверждением смещения.
- Ключ больше не содержит сервис и код ошибки. Выбрать объекты одного сервиса или кода можно только перебором префикса дня и чтением метаданных: каждый объект — отдельный `HEAD`. Скорость на объёме за полгода не измерена (не проверено).
- Повторная публикация одного исходного сообщения сборщиком (публикация дошла до брокера, сборщик упал до подтверждения смещения `events`) даёт новую запись `failed-events` с другим смещением и потому второй объект с теми же координатами исходного сообщения в теле. Первая редакция этого случая избегала. Дубль безопасен: содержимое совпадает, отличаются `failedAt` и `traceId`, если трасса новая. Окно узкое (публикация синхронная, `acks=all`), число таких дублей на стенде не измерялось (не проверено).
- Если запись сначала записана как `unreadable`, а схема потом появилась, объект остаётся `unreadable` с исходными байтами. Повторная запись вернёт 412. Разобрать такой объект можно вручную по base64; автоматической перезаписи нет.
- Объект после записи не меняется. Исправленное содержимое требует нового объекта, и это осознанно.
- Если объект записан с ошибочным содержимым, повторная доставка не исправит его: ключ тот же, запись вернёт 412. Исправление требует ручного удаления объекта; процедуры в проекте нет (не проверено).
- Восстановление байт из JSON декодированием base64 проверено только на уровне записи объекта (см. research.md R5); отдельного теста «JSON → байты → sha256» нет (не проверено; тест JSON-документа — T035).
- Возврат объекта (ADR-0019) выбирает объекты по префиксу дня и метаданным, а не по префиксу кода.

## Рассмотренные варианты

- Два ключа: по координатам исходного сообщения и `unreadable/…` по координатам записи `failed-events` (первая редакция). Окно с двумя объектами на одну запись при сбое между записью и подтверждением. Отвергнуто по ревью PR #6.
- Ключ из координат исходного сообщения для читаемой записи и «координат записи» для нечитаемой, с проверкой наличия обоих ключей перед записью: HEAD по двум ключам — гонка между экземплярами. Отвергнуто.
- HEAD, затем PUT: гонка двух экземпляров процессора. Отвергнуто.
- Версионирование без условного PUT: новая версия на каждый повтор доставки (research.md, «Иллюстративные примеры исходной постановки», п. 11). Отвергнуто.
- Ключ с `deviceId` первым: неравномерный префикс, нет поиска по дню. Отвергнуто.
