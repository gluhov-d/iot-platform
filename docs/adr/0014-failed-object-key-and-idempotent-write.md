# ADR-0014: Ключ объекта в MinIO и идемпотентная запись

**Статус**: предложено, 2026-11-21 (на проверке дизайна) · **Спецификация**: [specs/002-failed-events](../../specs/002-failed-events/spec.md)

## Контекст

Процессор пишет по одному объекту на каждое сообщение `failed-events`. Повторная доставка неизбежна: сбой после отправки и до подтверждения смещения, перебалансировка группы, повторная публикация сборщиком. Если ключ строится из координат `failed-events` и времени записи, повторная публикация дает второй объект (ошибка иллюстративного примера исходной постановки, research.md, «Иллюстративные примеры исходной постановки», п. 1).

Поиск нужен через полгода: по сервису, коду, дню, трассе и устройству.

## Решение

- Ключ объекта: `<sourceService>/<yyyy>/<MM>/<dd>/<errorCode>/<sourceTopic>-<sourcePartition>-<sourceOffset>.json`. Дата — `sourceTimestamp` в UTC. Одно исходное сообщение дает один ключ независимо от числа публикаций.
- Нечитаемое сообщение `failed-events`: `unreadable/<yyyy>/<MM>/<dd>/failed-events-<partition>-<offset>.json`, дата — время записи в `failed-events` (правило — ADR-0018).
- Тело JSON содержит все поля `FailedEvent`. `key`, `value` и `headers` — base64 от исходных байтов. Времена — ISO-8601 UTC.
- Запись в объект: `PutObject` с `If-None-Match: *`. Ответ 412 означает, что объект уже записан; сообщение считается обработанным и смещение подтверждается. Версия не создаётся (см. research.md R5: `bitnamilegacy/minio` и `pgsty/minio`).
- HEAD с последующим PUT не используется: между двумя экземплярами процессора это гонка.
- Содержимое при повторе не сравнивается: 412 означает «объект с таким ключом уже есть». Ключ однозначно задаёт исходное сообщение, поэтому сравнение не нужно.
- Метаданные объекта: `x-amz-meta-error-code`, `x-amz-meta-source-service`, `x-amz-meta-device-id`, `x-amz-meta-trace-id`.
- Поиск через полгода: ListObjectsV2 по префиксу сервис → дата → код; `traceId` и `deviceId` — по метаданным объекта или полю JSON. Полнотекстовый поиск — выгрузкой дня в ClickHouse или скриптом.

## Последствия

- Повторная доставка и повторная публикация одного сообщения не создают дубликатов.
- Объект после записи не меняется. Исправленное содержимое требует нового объекта, и это осознанно.
- Префикс по коду и дню позволяет найти пачку объектов одного кода (нужно для возврата, ADR-0019).
- Если объект записан с ошибочным содержимым, повторная публикация не исправит его: ключ тот же, запись вернёт 412. Исправление требует ручного удаления объекта; процедуры в проекте нет (не проверено).
- Поиск по `deviceId` и `traceId` идёт по префиксу дня, индекса нет. Скорость на объёме за полгода не измерена (не проверено).
- Восстановление байт из JSON декодированием base64 проверено только на уровне записи объекта (см. research.md R5); отдельного теста «JSON → байты → sha256» нет (не проверено; тест JSON-документа — T035).

## Рассмотренные варианты

- Ключ из координат `failed-events` и времени записи: дубль при повторной публикации. Отвергнуто.
- HEAD, затем PUT: гонка двух экземпляров процессора. Отвергнуто.
- Версионирование без условного PUT: новая версия на каждый повтор доставки (research.md, «Иллюстративные примеры исходной постановки», п. 11). Отвергнуто.
- Ключ с `deviceId` первым: неравномерный префикс, нет поиска по дню и сервису. Отвергнуто.
