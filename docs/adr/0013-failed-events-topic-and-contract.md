# ADR-0013: Единая тема failed-events и контракт FailedEvent

**Статус**: предложено, 2026-11-21 (на проверке дизайна); дополнено 2026-11-26 по ревью PR #7 (заголовки — упорядоченный список `headerList`, avros 1.5.0) · **Спецификация**: [specs/002-failed-events](../../specs/002-failed-events/spec.md)

## Контекст

Сообщения, которые сборщики не смогли обработать, уходили в две темы: `events-dlt` (приём событий) и `devices-dlt` (реестр устройств). Обе темы никто не читал, кроме ручного просмотра, и у каждой свои переменные окружения, subjects в Schema Registry и тесты. Задание требует одну тему `failed-events`, из которой процессор пишет объекты в MinIO.

Прежний формат не сохранял исходные байты. При ошибке десериализации сборщик не имел исходного массива, а пересериализация меняет байты (id схемы в заголовке). Требование «исходное сообщение восстанавливается байт в байт» без явного контракта не выполнить.

## Решение

- Тема `failed-events`: 3 раздела, `cleanup.policy=delete`, `retention.ms` = `KAFKA_FAILED_EVENTS_RETENTION_MS` (14 суток), без `retention.bytes`: всплеск ошибок не должен удалить ещё не архивированные сообщения. Ключ сообщения — `<sourceTopic>-<sourcePartition>-<sourceOffset>`.
- Контракт `FailedEvent` в `avros/avro/failed-event.avsc`, avros 1.4.0, subject `failed-events-value`, совместимость FULL_TRANSITIVE.
- Поля минимума задания: исходные топик, партиция и смещение; `sourceService`; `failedAt`; `errorCode`; `errorType`; `description`; `traceId`; `key` и `value` как `bytes` (сырые байты до разбора).
- Поля сверх минимума: `sourceTimestamp` (дата ключа объекта; одинакова у повторных публикаций), `headers` (исходные заголовки без служебных; нужны для восстановления и возврата; с 1.5.0 — см. ниже), `attempts` (число вызовов обработчика), `deviceId` (поиск по устройству через полгода; null, если сообщение не разобрано; совместимость поля — `make avros-check`, research R9).
- Заголовки (дополнено 2026-11-26): `map` не хранит повторяющиеся имена заголовков Kafka и заголовки со значением `null` — после возврата
  у сообщения другой набор заголовков. В avros 1.5.0 добавлено поле `headerList`: упорядоченный список `SourceHeader {name, value: null | bytes}`,
  `default null`, со всеми заголовками в исходном порядке. Поле `headers` (`map`) остаётся и заполняется как в 1.4.0: заменить его тип
  несовместимо с FULL_TRANSITIVE, а читатель 1.4.0 без него потерял бы заголовки. Читатель 1.5.0 берёт `headerList`, при `null` — `headers`
  (запись писателя 1.4.0). Проверка совместимости — research.md R26.
- `ErrorCode` — единственный справочник кодов платформы: `UNKNOWN`, `DESERIALIZATION_FAILED`, `VALIDATION_FAILED`, `STORAGE_UNAVAILABLE`, `PROCESSING_FAILED`; у enum задан `default` = `UNKNOWN`. Проверено на прототипе (см. research.md R9): добавленный символ проходит FULL_TRANSITIVE, старый читатель видит `UNKNOWN`.
- Ключ с невалидным UTF-8 читается строгим декодером; такая ошибка даёт `DESERIALIZATION_FAILED` с исходными байтами (см. research.md R2: со `StringDeserializer` байты терялись).
- `events-dlt` и `devices-dlt` удаляются полностью: строки в `init-topics.sh`, переменные `KAFKA_*_DLT_TOPIC`, subjects `*-dlt-value`, код и тесты DLT. `--delete --if-exists` необратим: перед выполнением на стенде владелец должен подтвердить, что содержимое DLT не нужно.
- Каждый сборщик имеет свою реализацию `FailedEventRecoverer` (adapter/out/kafka). Общим остаётся только контракт, общий модуль Gradle не вводится.
- device-service топики не читает и не меняется.
- Порядок выкладки: новый код ошибки — сначала процессор, потом сборщики.

## Последствия

- Все необработанные сообщения лежат в одной теме одним контрактом; процессор читает одну тему.
- Новые коды добавляются без поломки старых читателей при условии `default` у enum.
- С 1.5.0 сборщики пишут заголовки дважды (`headerList` и `headers`): небольшой лишний объём ради читателей 1.4.0. Удалить `headers` можно
  только новой мажорной версией контракта, когда читателей 1.4.0 не останется.
- Тема хранит 14 суток. Отставание группы процессора видно через kafka-exporter; панель и порог — в наблюдаемости.
- Старое содержимое `events-dlt` и `devices-dlt` не переносится. Нужно ли его сохранить до удаления, решает владелец стенда; в проектных материалах решения нет (не проверено).
- Сборщики пересериализацию не делают: байты берутся из обёртки-десериализатора до разбора (см. research.md R1: sha256 совпал).

## Рассмотренные варианты

- Оставить две DLT-темы: два формата, два набора правил и два пути для процессора. Отвергнуто.
- Общий модуль Gradle для публикации FailedEvent в сборщиках. Отвергнуто: сервисы независимы, общим должен быть только контракт.
- JSON в теме вместо Avro: нет проверки совместимости и нет байтового контракта. Отвергнуто.
- Заменить тип `headers` на список: несовместимо с FULL_TRANSITIVE. Отвергнуто.
- `map<string, array<bytes>>`: сохраняет повторы одного имени, но теряет порядок между разными именами. Отвергнуто.
- Ключ по `deviceId`: при шумном устройстве и при null-ключе исходного сообщения разделы неравномерны. Отвергнуто.
