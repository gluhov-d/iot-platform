# ADR-0003: Кэш сбрасывает владелец данных после COMMIT

**Статус**: предложено, 2026-11-11 · **Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

Чтение — Cache-Aside (Redis → реплики). Запись асинхронная, а реплика отстаёт от основного узла. Сброс ключа
device-service при отправке команды бесполезен: следующее чтение возьмёт с реплики старые данные и снова положит их
в кэш. Сброс device-collector-service после записи — та же гонка, только короче. Перезапись кэша новым значением
опасна при параллельных изменениях.

## Решение

- В `devices` появляется `version` — номер применённого изменения (растёт при каждом `APPLIED`).
- Кэш `device:v1:{deviceId}` — hash: `body` (готовый ответ) и `version`; TTL `DEVICE_CACHE_TTL` на ключ.
- Порог — отдельный ключ `device:v1:floor:{deviceId}` со своим сроком `DEVICE_CACHE_FLOOR_TTL`
  (больше `DEVICE_CACHE_TTL`): в одном ключе с ответом он истекал вместе с ним, и при отставании реплики дольше
  `DEVICE_CACHE_TTL` старая версия снова попадала в кэш (замечание ревью дизайна).
- device-collector-service после `COMMIT` выполняет Lua: `floor = max(floor, version)`, срок ключа порога
  продлевается, `body` с меньшей версией удаляется. Ошибка Redis — WARN и метрика, ack сообщения не задерживается.
- device-service при промахе пишет в кэш (Lua) только если версия строки реплики `≥ floor` и не меньше уже лежащей;
  иначе отдаёт данные реплики без кэширования (`device_cache_requests_total{result="stale_replica"}`). Запись принята —
  ключ порога удаляется: реплика догнала, держать порог больше не нужно.

## Последствия

- Старые данные не попадают в кэш ни при отставании реплики, ни в гонке «чтение — запись — сброс — запись в кэш»
  (`ds-cache-consistency-sequence.mmd`), в том числе когда отставание переживает `DEVICE_CACHE_TTL`.
- Пока реплика не догнала, каждый GET этого устройства идёт в реплику — окно ограничено отставанием.
- Ключ порога живёт до первого чтения версии не ниже порога, но не дольше `DEVICE_CACHE_FLOOR_TTL`: срок выбирается
  больше худшего ожидаемого отставания реплики. Если отставание переживёт и его, старые данные могут вернуться ещё на
  один `DEVICE_CACHE_TTL` — известное ограничение (README).
- Второй ключ на устройство: расход памяти — только у устройств, чьё изменение реплика ещё не отдаёт; после успешного
  чтения ключ удаляется.
- Redis недоступен при сбросе — устаревание ограничено `DEVICE_CACHE_TTL`. Это осознанный компромисс: остановка
  обработки темы из-за кэша хуже.

## Рассмотренные варианты

Сброс device-service после отправки; DEL в device-collector-service без версии; повторный сброс через задержку
(эвристика, зависит от величины отставания); чтение с основного узла после промаха (нарушает FR-019); порог в том же
хеше со сроком по полю (`HEXPIRE`, Redis 7.4+ — требует проверки на Lettuce и в Lua, выигрыш только в одном ключе).
