# ADR-0003: Кэш сбрасывает владелец данных после COMMIT

**Статус**: предложено, 2026-11-11 · **Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

Чтение — Cache-Aside (Redis → реплики). Запись асинхронная, а реплика отстаёт от основного узла. Сброс ключа
device-service при отправке команды бесполезен: следующее чтение возьмёт с реплики старые данные и снова положит их
в кэш. Сброс device-collector-service после записи — та же гонка, только короче. Перезапись кэша новым значением
опасна при параллельных изменениях.

## Решение

- В `devices` появляется `version` — номер применённого изменения (растёт при каждом `APPLIED`).
- Кэш `device:v1:{deviceId}` — hash: `body` (готовый ответ), `version`, `floor`; TTL `DEVICE_CACHE_TTL` на ключ.
- device-collector-service после `COMMIT` выполняет Lua: `floor = max(floor, version)`, `body` с меньшей версией
  удаляется. Ошибка Redis — WARN и метрика, ack сообщения не задерживается.
- device-service при промахе пишет в кэш (Lua) только если версия строки реплики `≥ floor` и не меньше уже лежащей;
  иначе отдаёт данные реплики без кэширования (`device_cache_requests_total{result="stale_replica"}`).

## Последствия

- Старые данные не попадают в кэш ни при отставании реплики, ни в гонке «чтение — запись — сброс — запись в кэш»
  (`ds-cache-consistency-sequence.mmd`).
- Пока реплика не догнала, каждый GET этого устройства идёт в реплику — короткое окно, ограничено отставанием.
- Redis недоступен при сбросе — устаревание ограничено TTL. Это осознанный компромисс: остановка обработки темы
  из-за кэша хуже.

## Рассмотренные варианты

Сброс device-service после отправки; DEL в device-collector-service без версии; повторный сброс через задержку
(эвристика, зависит от величины отставания); чтение с основного узла после промаха (нарушает FR-019).
