# ADR-0017: Копии PostgreSQL и ClickHouse в MinIO контейнером backup-runner

**Статус**: предложено, 2026-11-21 (на проверке дизайна) · **Спецификация**: [specs/002-failed-events](../../specs/002-failed-events/spec.md)

## Контекст

Копии шардов PostgreSQL (`shard-backup.sh`, реестр устройств) и копия ClickHouse должны уходить в MinIO по расписанию, а восстановление должно работать из копии, взятой из MinIO. Задание не требует восстановления на произвольный момент времени (PITR).

## Решение

- Контейнер `backup-runner` в стенде: busybox crond, расписание `BACKUP_SCHEDULE` (по умолчанию `0 3 * * *` UTC), разовый запуск через `make backup`.
- PostgreSQL: логика `shard-backup.sh`. Позиции группы Kafka снимаются до `pg_dump`; `pg_dump` идет с реплик; `manifest.txt` содержит смещения по каждому разделу. Загрузка в `backups/postgres/<метка>/` пользователем `backup-postgres`. Проверено на прототипе (см. research.md R18): позиции `0:0,1:40` записаны, `verify-restore` дал MATCH, cron выполнил 4 запуска подряд без ошибок. Логика копии шарда — один общий скрипт `shard-backup.sh`: его вызывают `make shard-backup` (локальная копия, как раньше) и backup-runner (копия в MinIO); второй реализации нет.
- ClickHouse: `BACKUP DATABASE … TO S3(backup_s3, …)` по HTTP. Ключи берутся из named collection `backup_s3` (`from_env`), в тексте запроса ключей нет (см. research.md R17). Выгрузка в `backups/clickhouse/<метка>/`. В `SETTINGS` указывается уникальный `id`: повтор с тем же id отвергается (см. research.md R17).
- Образ: `FROM apache/kafka:4.2.0` (для `kafka-consumer-groups`), клиенты `pg_dump`, `pg_restore`, `psql` 18.6 копируются из `postgres:18.6-alpine`, `mc` из `pgsty/mc`, busybox crond. Добавка к базовому образу — 59 МБ (см. research.md R18). Пользователь образа — root, иначе crond не запустится. Переменные окружения crond не передаёт: entrypoint пишет `/etc/backup.env` (права 600), задания читают его (см. research.md R18).
- Восстановление: `make shard-restore FROM=minio BACKUP=<метка> CONFIRM=yes` (скачать и затем прежний restore) и `make clickhouse-restore BACKUP=<метка>`. Проверено по компонентам: `pg_restore` из копии в MinIO дал совпадение `count:sum` (см. research.md R18); `RESTORE DATABASE … FROM S3` дал совпадение контрольной суммы (см. research.md R17). Сквозного запуска целевых `make`-команд не проверялось; шаги описываются в README.

## Последствия

- Копии лежат в MinIO по расписанию, срок хранения 30 суток (ADR-0015).
- `pg_dump` — логический снимок, не PITR. Потеря данных между копиями возможна; интервал определяется расписанием (сутки по умолчанию).
- Позиции группы в manifest — основа для отката смещений при восстановлении. Сброс смещений группы при восстановлении не проверен: позиции записаны, но обратно в группу не возвращались (см. research.md R18).
- Образ на JDK 21 из `apache/kafka:4.2.0`: инструменты работают; на JDK 25 не проверено.
- В тесте `pg_dump` шёл под суперпользователем. Для копии нужна отдельная роль только на чтение; её нет в проверенном варианте (не проверено).
- Параллельные копии: `flock -n` не даёт двум заданиям идти одновременно; при длинной копии срабатывание не воспроизводилось (не проверено).
- Пути копий для локального хранения вне этого ADR; что остаётся на диске, решается при реализации.
- Имя проекта, расписание, учётки и адреса MinIO задаются переменными окружения (`.env.example`); значений в образе и в репозитории нет.
- Копии PostgreSQL и ClickHouse запускаются из одного контейнера по одному расписанию; сбой одной не отменяет другую (ожидание, не проверено). Поведение при одновременном сбое не проверено.
- Восстановление из копии возвращает данные на момент копии: всё, что записано после, нужно доливать из топиков или повторной доставкой (не проверено на объёме стенда).

## Рассмотренные варианты

- WAL-G и pgBackRest: дают PITR, но требуют архивации WAL и отдельной настройки хранилища. Задание PITR не требует. Отвергнуто.
- Cron на хосте вне стенда: не входит в стенд и не воспроизводится в compose. Отвергнуто.
- Отдельный образ с Kafka-инструментами (1,11 ГБ): объединённый образ дал 735 МБ при тех же инструментах (см. research.md R18). Отвергнуто.
- Логический `pg_dump` с реплик, как в `shard-backup.sh`: основа решения, см. «Решение».
