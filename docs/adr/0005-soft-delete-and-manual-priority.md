# ADR-0005: Мягкое удаление и приоритет ручных изменений

**Статус**: предложено, 2026-11-13 · **Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

У записи устройства два источника изменений: события роутера и команды администратора. Нужно решить, что делает
удаление, что будет, если после него придёт событие роутера, и чья правка важнее. Сравнение по времени ненадёжно:
время события роутера — по часам устройства.

## Решение

- Удаление мягкое: запись остаётся с отметкой «удалено администратором», чтение отвечает `404`. Запоздалое или новое
  событие роутера такое устройство не возвращает; вернуть его может только `POST`.
- Поля делятся на две группы ([data-model.md](../../specs/001-device-service/data-model.md)): поля администратора после
  первой команды меняют только команды; данные устройства (прошивка, ОС, сенсоры, время активности) — только роутер.
- Команда сравнивается по времени только с предыдущей командой, событие роутера — с предыдущим событием роутера: часы
  устройства не делают команду устаревшей.
- Удаление по событию роутера работает как раньше: более новое событие с данными устройства его снимает.
- Полная таблица исходов — требование FR-015 в [spec.md](../../specs/001-device-service/spec.md), поток — `diagrams/dcs-operations-sequence.mmd`.

## Последствия

- Решение администратора не теряется из-за запоздалых или повторных событий; каждое отклонённое сообщение остаётся
  в журнале обработки с исходом `IGNORED` или `STALE`.
- Между двумя администраторами побеждает команда, принятая позже; оптимистичной блокировки (ETag, If-Match) нет:
  проверка шла бы по отстающей модели чтения.
- Повторное чтение темы зависит от того, что команды не сжаты ([ADR-0010](0010-devices-topic-compaction-lag.md)).

## Рассмотренные варианты

Физическое удаление (запоздалое событие создаст устройство заново, следов удаления нет); правило последней записи по
времени для всех сообщений (часы устройств расходятся).
