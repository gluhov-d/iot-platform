# ADR-0005: Мягкое удаление и приоритет ручных изменений

**Статус**: предложено, 2026-11-11 · **Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

У записи устройства два источника изменений: события роутера и команды администратора. Нужно решить, что делает
удаление и что будет, если после него придёт событие роутера; чья правка важнее. Сравнение по времени ненадёжно:
время события роутера — по часам устройства.

## Решение

- Удаление мягкое: `status = DELETED`, `deleted_at`, `deleted_by = ADMIN`; если строки нет — вставляется
  надгробие. GET отвечает `404`.
- Событие роутера после удаления администратором — исход `IGNORED`: в журнале и `seen_count`, данные не меняются,
  устройство не воскресает. Вернуть устройство можно только `POST` (`CREATE` снимает удаление).
- `UPDATE` удалённого устройства — `IGNORED`. `DELETE` повторно — то же состояние.
- Поля администратора (`name`, `tenant_id`, `owner_id`, `device_type`, `serial_number`, `manufacturer`, `model`,
  `status`, `settings`, `attributes`) после первой команды (`managed_at`) меняют только команды. Поля устройства
  (прошивка, ОС, сенсоры, `last_seen_at`, `registered_at`) — только роутер, как раньше.
- Время команды сравнивается с `managed_at`, время события роутера — с `last_state_at`: часы устройства не делают
  команду устаревшей. Между командами — последняя по времени приёма (часы device-service, NTP).
- Удаление роутером (`eventType = DELETED`) — как раньше, `deleted_by = DEVICE`, более новый снимок роутера его снимает.

## Последствия

- Решение администратора не теряется из-за запоздалых или повторных событий; история — в журнале.
- Оптимистичной блокировки между двумя администраторами (ETag/If-Match) нет: проверка шла бы по отстающей модели
  чтения. Ограничение записано; при необходимости — версия в команде и проверка у владельца.

## Рассмотренные варианты

Физическое удаление (запоздалое событие воскресит устройство, следов нет); правило последней записи по времени
(часы устройств расходятся).
