# ADR-0011: Тема devices хранит сообщения вместо сжатия

**Статус**: принято, 2026-11-17 (дополнено 2026-11-18: смещения группы без тихого сброса; 2026-11-19: раздел, появившийся у работающей группы) · заменяет [ADR-0010](0010-devices-topic-compaction-lag.md) ·
**Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

По ADR-0010 тема `devices` оставалась сжимаемой (`cleanup.policy=compact`), а потеря команд администратора
откладывалась настройкой `min.compaction.lag.ms` (7 суток) и правилом «копия шардов не реже этого срока».

Ревью дизайна показало, что это только отсрочка. В теме с ключом `deviceId` смешаны команды администратора и снимки
роутера, и сжатие оставляет на ключ последнее сообщение, то есть уничтожает порядок. Последовательность
«`DELETE` 10:20 → снимок роутера 10:25» через срок сжатия превращается в один снимок: обработчик, который читает тему
повторно (сброс смещений группы при восстановлении шардов из копии) или просто отстал дольше срока, увидит только
снимок — удалённое устройство станет активным, а ручные поля из `UPDATE` будут перезаписаны. Увеличение срока
сдвигает границу, но не убирает случай.

Полное итоговое состояние на ключ (второй допустимый вариант) потребовало бы, чтобы каждый производитель знал поля
администратора и признак удаления. events-collector-service их не знает: он публикует данные устройства из событий.
Значит, писать такое состояние мог бы только владелец реестра (device-collector-service) в отдельную тему-журнал
состояния — заметный объём работ ради того же результата.

## Решение

- У темы `devices` — `cleanup.policy=delete` и `retention.ms` = `KAFKA_DEVICES_RETENTION_MS` (по умолчанию 30 суток).
  Сжатие выключено: сообщения ключа хранятся целиком и в исходном порядке, пока не выйдут за срок хранения.
- Правило эксплуатации прежнее: копия шардов (`make shard-backup`) делается не реже срока хранения. Тогда всё, что
  придётся читать повторно после восстановления, ещё лежит в теме.
- `shard-restore.sh` сравнивает возраст копии со сроком хранения и предупреждает, если копия старше.
- Ключ `deviceId` остаётся требованием контракта (раздел и порядок обработки устройства), хотя тема с политикой
  `delete` приняла бы и сообщение без ключа.
- Переход существующей темы — `kafka-configs --alter` в `init-topics.sh`: `cleanup.policy=delete`, `retention.ms`,
  и `--delete-config min.compaction.lag.ms`.
- У device-collector-service `auto-offset-reset: none`. С `earliest` потребитель, чьё смещение вышло за диапазон темы,
  молча переходил бы на самое раннее сохранённое сообщение: обработчик, отставший дольше срока хранения, применил бы
  событие роутера после уже удалённого `DELETE` — та же потеря, что при сжатии, только позже. Поэтому:
  - раздел без подтверждённого смещения (новая группа, новый раздел) читается с начала: перед первым `poll`
    обработчика группе через Admin выставляется самое раннее смещение таких разделов (`DevicesConsumerOffsets`).
    Через rebalance listener не получается: Spring Kafka для `@KafkaListener` спрашивает `position()` раньше него,
    и с `none` это `NoOffsetForPartitionException` (проверено на Spring Kafka 4.0.3);
  - то же для раздела, который появился у работающей группы (число разделов увеличено без перезапуска сервиса): он
    тоже читается с начала, без перезапуска и при любом числе экземпляров. Установка смещения только перед первым
    `poll` этого не покрывала — обработчик останавливался с `NoOffsetForPartitionException` (ревью реализации,
    PR #5). Адаптер `@KafkaListener` реализует `ConsumerSeekAware`, поэтому Spring Kafka 4.0.3 вызывает
    `position()` при назначении раздела; ошибка в обработчик ошибок не попадает, контейнер считает её фатальной
    и останавливается (R16 не подтвердилось). Механизм (R18, проверен в T127: один и два экземпляра в одной группе): `Consumer`
    оборачивается (`DefaultKafkaConsumerFactory.addPostProcessor`, `java.lang.reflect.Proxy`), и
    `NoOffsetForPartitionException` из `position(...)` и `poll(...)` приводит к `seekToBeginning` для этих разделов
    и одному повтору вызова — в потоке потребителя, поэтому другие участники группы не мешают. Новый раздел
    потребитель замечает при обновлении метаданных (`metadata.max.age.ms`,
    `DEVICES_CONSUMER_METADATA_MAX_AGE_MS`).
  - смещение вне диапазона темы останавливает обработчик: ERROR в логе, health `DOWN` (контейнер unhealthy), более
    поздние сообщения не применяются. Дальше решает оператор: восстановить шарды из свежей копии (смещения группы
    из её manifest) или осознанно сдвинуть смещение группы и перезапустить сервис;
  - остановка обработчика `devices` по любой причине (смещение вне диапазона, не удалось выставить смещение нового
    раздела) — health `DOWN`.

## Последствия

- Порядок «команда → событие роутера» сохраняется, пока сообщения в теме: повторное и отставшее чтение дают то же
  состояние, что и первая обработка. Удалённое устройство само не возвращается.
- Выход за срок хранения теперь не подменяет историю, а убирает её целиком; восстановление из копии старше срока
  предупреждает, а смещение группы вне диапазона темы останавливает обработчик (`auto-offset-reset: none`) вместо
  тихого перехода на начало темы и применения более позднего снимка. Проверено интеграционным тестом
  `ItConsumerOffsetsTest`: сообщения до смещения удалены (`deleteRecords`) — обработчик остановлен, событие роутера
  не применено, health `DOWN`.
- Цена: такой сбой требует действия оператора — сервис сам не продолжит. Это осознанно: продолжение означало бы
  применить изменения поверх потерянных.
- Тема растёт за срок хранения: на учебных объёмах (тысячи устройств, единицы сообщений в секунду) несущественно.
- Потребителю, которому нужен последний снимок по ключу, тема больше не даёт его «из коробки» — источник истины для
  чтения это реестр в PostgreSQL (`devices_read`), таких потребителей у темы нет.

## Рассмотренные варианты

Оставить `compact` с увеличенным `min.compaction.lag.ms` (отсрочка, случай остаётся — ADR-0010); отдельная тема команд
с политикой `delete` при сжимаемой `devices` (задание требует одну тему, порядок между командой и событием одного
устройства пришлось бы восстанавливать по правилам); полное итоговое состояние на ключ от владельца реестра
(отдельная тема-журнал состояния: наибольший объём работ, те же гарантии); принять потерю без защиты.

Смещение раздела, появившегося у работающей группы (R16, не подошли): установка смещения через Admin при старте
обработчика и его перезапуск после остановки `NO_OFFSET` — Admin меняет смещения только у группы без участников,
поэтому с несколькими экземплярами перезапуски не сходятся (на двух: `UnknownMemberIdException`, обработчик крутится в
цикле); обработчик ошибок контейнера — `NoOffsetForPartitionException` до него не доходит (контейнер останавливается
раньше); rebalance listener — Spring Kafka спрашивает `position()` раньше него; `auto-offset-reset: earliest` — тихий
сброс, см. выше.
