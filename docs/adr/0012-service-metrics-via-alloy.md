# ADR-0012: Метрики сервисов платформы собирает Alloy

**Статус**: принято, 2026-11-19 (ревью реализации, PR #5) · **Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

Grafana Alloy на стенде собирает логи контейнеров (Docker API → Loki) и принимает трассы (OTLP → Tempo). Метрики
сервисов платформы — events-collector-service, device-collector-service и обоих экземпляров device-service — Prometheus
забирал сам: задания в `prometheus.yml` с поиском экземпляров через DNS Docker, у device-service порт management-порта
записан в файл числом (Prometheus не подставляет переменные). Получалось два пути сбора телеметрии: логи и трассы —
через агент, метрики — мимо него. Ревью реализации попросило перенести обнаружение экземпляров и сбор
`/actuator/prometheus` в Alloy.

## Решение

- Alloy находит экземпляры сервисов платформы, опрашивает их `/actuator/prometheus` и передаёт метрики в Prometheus
  (`prometheus.remote_write`); Prometheus принимает их как приёмник remote write.
- Метки остаются прежними: `job` — имя сервиса (`events-collector-service`, `device-collector-service`,
  `device-service`), `instance` — адрес экземпляра; переименование `outbox_candidate_total` →
  `outbox_candidate_created_total` переезжает из `metric_relabel_configs` в правила Alloy. Запросы панелей Grafana
  не меняются.
- Порты берутся из окружения (`sys.env` в конфигурации Alloy): у device-service — `DEVICE_SERVICE_MANAGEMENT_PORT`
  вместо числа в `prometheus.yml`.
- Задания этих трёх сервисов из `prometheus.yml` удаляются. Экспортёры (PostgreSQL, Kafka), Proxy, Keycloak, MinIO и
  компоненты наблюдаемости Prometheus по-прежнему опрашивает сам: у них нет экземпляров, которые нужно находить, а
  перенос не меняет собираемых данных.

## Последствия

- Один агент отвечает за обнаружение экземпляров и доставку логов, трасс и метрик сервисов; новый экземпляр
  (`--scale`) попадает во все три потока одинаково.
- Метрики сервисов зависят от Alloy: при его остановке пропадают вместе с логами и трассами. `up` этих заданий
  формирует Alloy и передаёт вместе с метриками; страница Targets в Prometheus их больше не показывает — состояние сбора
  видно в интерфейсе Alloy.
- Prometheus запускается с приёмом remote write; Alloy стартует после Prometheus.

## Рассмотренные варианты

Оставить прямой сбор Prometheus (два пути сбора телеметрии, замечание ревью); перенести в Alloy и экспортёры со
сторонними компонентами (лишняя работа без новых данных, может быть сделано отдельно); отправлять метрики из сервисов
по OTLP (меняет код всех сервисов и имена метрик, панели пришлось бы переписать).
