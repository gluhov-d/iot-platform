# ADR-0021: Выдача команды опросом ровно один раз

**Статус**: предложено, 2026-11-28 (на проверке дизайна). Спецификация — [specs/003-router-manager](../../specs/003-router-manager/spec.md).

## Контекст

Задание: роутер запрашивает команду с интервалом, отсутствие команды — штатный ответ, одна команда выдаётся один раз и при двух
экземплярах, повторный ответ роутера не меняет итог. Нужно выбрать тип вызова и способ выдачи без блокировок между экземплярами.

## Решение

- Унарный `PollCommand`: каждый вызов балансируется отдельно (`round_robin` по DNS двух экземпляров, research.md R11), имеет свой
  срок и спокойно повторяется. Поток держал бы соединение на одном экземпляре; на миллионах роутеров — миллионы открытых потоков
  и ручная балансировка при перезапуске. Сравнение — в необязательной части (FR-027).
- Выдача — одно выражение: `UPDATE … SET status='SENT' WHERE command_id = (SELECT … ORDER BY created_at, command_id LIMIT 1
  FOR UPDATE SKIP LOCKED) RETURNING …`. Второй экземпляр пропускает заблокированную строку, а не ждёт её (R1: 500 из 500 уникально).
- Накопилось несколько команд — выдаются по одной в порядке создания; `more_pending` говорит роутеру опросить сразу.
- Ответ роутера — `UPDATE … WHERE status='SENT'`; повтор и ответ после итога — 0 строк, `applied = false`, итог не меняется (R3).
- Потерянный ответ с командой повторно не выдаётся (ADR-0025).

## Рассмотренные варианты

- Серверный поток `WatchCommands` — в необязательной части со сравнением под нагрузкой.
- `SELECT … FOR UPDATE` без `SKIP LOCKED` — экземпляры ждут друг друга на одной строке.
- Аренда команды в Redis — второй источник истины для статуса, нарушает «один владелец данных».

## Последствия

- Задержка выдачи — до интервала опроса; ускоряется только при `more_pending`.
- Каждый промах кэша — одно `UPDATE` по частичному индексу `status = 'NEW'`.
