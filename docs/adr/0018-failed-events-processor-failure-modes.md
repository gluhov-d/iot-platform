# ADR-0018: Поведение failed-events-processor при сбоях

**Статус**: предложено, 2026-11-21 (на проверке дизайна); дополнено 2026-11-22 по ревью PR #6 (общий ключ для читаемой и нечитаемой записи, ADR-0014) · **Спецификация**: [specs/002-failed-events](../../specs/002-failed-events/spec.md)

## Контекст

Процессор — последнее звено пути ошибки. Нужно решить четыре случая: сообщение, которое процессор сам не может разобрать; недоступность MinIO; временная ошибка Schema Registry; всплеск, когда БД недоступна и весь поток уходит в `failed-events`.

## Решение

- Нечитаемое сообщение (не Avro, 404 схемы, мусор): объект с тем же ключом, что и у обычного (ADR-0014): `<yyyy>/<MM>/<dd>/failed-events-<partition>-<offset>.json`, дата — время записи в `failed-events`. Тело — `kind = unreadable`, base64 ключа, значения и заголовков, причина. Единый ключ закрывает окно «записан `unreadable`, процесс упал до подтверждения, схема восстановилась, запись разобрана»: вторая запись попадает на тот же ключ и получает 412. Затем смещение подтверждается (см. research.md R7).
- Временная ошибка Schema Registry (сеть, 5xx): повторы без предела, объект `unreadable` не пишется. Ошибка 404 схемы и ошибка разбора — объект с `kind = unreadable`. Проверено на прототипе (см. research.md R7): при паузе Schema Registry объекта не было; после возврата появился.
- Недоступность MinIO: `DefaultErrorHandler` с бесконечным `ExponentialBackOff` (максимум 10 с), `ContainerPausingBackOffHandler` и тайм-ауты SDK: `apiCallTimeout` 8 с, `apiCallAttemptTimeout` 4 с. Тайм-ауты меньше `max.poll.interval.ms`. Проверено на s3mock и на MinIO (см. research.md R6): пауза 45 с, группа остаётся `Stable`, смещение подтверждается после возврата, объект один.
- Без тайм-аута SDK потребитель выпадал из группы через `max.poll.interval.ms` (см. research.md R6, варианты 1 и 2). Пауза контейнера без тайм-аута SDK не помогает: блокировка идёт внутри вызова S3.
- Своего DLT у процессора нет. При неудачной записи сообщение не подтверждается и остаётся в `failed-events` до восстановления, в пределах 14 суток retention.
- Всплеск (БД недоступна, поток `STORAGE_UNAVAILABLE`): процессор пишет по одному объекту на сообщение в своём темпе. Отставание растёт и видно на панели группы; основная тема не страдает. Запас — 14 суток retention. Скорость процессора в объектах в секунду не замерена (проверка на стенде).
- Предохранитель «пауза потребления сборщика при массовых ошибках БД» отвергнут: он меняет поведение сборщиков сверх задания. Может быть добавлен позже отдельным решением.
- Бесконечный повтор при недоступном MinIO прерывается только восстановлением MinIO или остановкой контейнера оператором. Автоматический сигнал — отставание группы на панели.
- Тайм-ауты SDK и параметры повторов задаются переменными окружения, в `application.yaml` чисел нет (правило проекта). Конкретные значения взяты из прототипа и подлежат проверке при реализации.

## Последствия

- Сообщение не теряется: выход из потока только через объект в MinIO (в том числе с `kind = unreadable`).
- Пауза MinIO — ожидание, а не сбой: группа `Stable`, но обработка стоит. Сигнал оператору — отставание группы и ошибки записи.
- Открытый риск: постоянная ошибка записи, не связанная с недоступностью (например, отказ в правах 403), обрабатывается как временная. Процессор застрянет на разделе. Поведение не проверено, решения в проектных материалах нет.
- Retention 14 суток — жёсткая граница: если MinIO недоступен дольше, сообщения удаляются до записи.
- Повторы сборщика: `attempts` — число вызовов обработчика; `ExponentialBackOffWithMaxRetries(n)` делает n+1 вызовов (см. research.md R3), это учитывается в поле `attempts`.

## Рассмотренные варианты

- Собственный DLT у процессора: цепочка ошибок без конца. Отвергнуто.
- Пауза потребления сборщиков при массовых ошибках БД: см. Решение. Отвергнуто.
- `sleep` в потоке обработчика вместо паузы контейнера: вылет из группы (см. research.md R6). Отвергнуто.
- Запись `unreadable` при ошибке Schema Registry: временный сбой дал бы ложный `unreadable` (см. research.md R7). Отвергнуто.
- Каскад из двух обработчиков: вне этого ADR, см. ADR-0019.
