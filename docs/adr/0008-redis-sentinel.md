# ADR-0008: Redis через Sentinel для всей платформы

**Статус**: предложено, 2026-11-11 · **Спецификация**: [specs/001-device-service](../../specs/001-device-service/spec.md)

## Контекст

Redis общий: в нём аренда публикатора и отпечатки events-collector-service, кэш device-service, сброс кэша
device-collector-service. Задание требует подключение через Sentinel. Сейчас один узел без резерва.

## Решение

- В Compose: `redis` (master), `redis-replica`, `redis-sentinel-1..3` (кворум 2, имя master `platform-redis`,
  `resolve-hostnames`/`announce-hostnames`).
- Все сервисы подключаются через Sentinel (`REDIS_SENTINEL_MASTER`, `REDIS_SENTINEL_NODES`), Lettuce сам находит
  текущий master; пароль — `REDIS_PASSWORD`.
- Политика памяти — `volatile-lru` с `maxmemory`: вытесняются только ключи с TTL (кэш устройств, аренда), отпечатки
  `devices:fingerprint` без TTL не трогаются. Вытеснение аренды равносильно её истечению — его уже выдерживает
  проверка `ownerToken` при записи отметок публикации.

## Последствия

- Отказ master — переключение без перезапуска сервисов (проверка стенда).
- Асинхронная репликация Redis: при переключении можно потерять последние записи — для кэша это промах, для аренды
  ограничено её TTL, для отпечатка — лишняя публикация (дедупликация у потребителя).
- `allkeys-lru`, как советует теория для чистого кэша, здесь опасен: вытеснил бы отпечатки, и events-collector-service
  заново опубликовал бы неизменившиеся устройства.

## Рассмотренные варианты

Redis Cluster (масштабирование, а не доступность; Lua по нескольким ключам ограничена слотами); отдельный Redis
только для device-service (задание требует общий).
