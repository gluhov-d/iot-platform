# Research: device-service

Решения о сторонних компонентах. «Проверено» — выполнено при подготовке дизайна; «на прототипе» — на одноразовом стенде
(Spring Boot 4.0.3, Java 25, Keycloak 26.0.8, Redis 8.6.7, ShardingSphere-Proxy 5.5.3), код прототипа в репозиторий не
входит. «Предположение» — не проверялось: первая задача соответствующего блока tasks.md проверяет его до зависящего
кода; не подтвердилось — агент останавливается, применяется запасной вариант, правятся plan.md и ADR, повторяется `analyze`.

## Результаты проверок на стенде

**T068 — отказ основного узла Redis (R9, R10, R14, FR-020, FR-021).** Основной `iot-redis` остановлен в 21:52:21 UTC на работающем
стенде. Пока он был остановлен (≈10 мин), прошли `make dcs-quick-check` (21:57, 21:59) и `make ds-quick-check`: POST → GET на другой
реплике, PUT и DELETE в пределах 5 с, обработка сообщений `devices` на обоих шардах — без перезапуска сервисов. В логах
device-service за это время нет ошибок Redis. Sentinel назначил основным узел `redis-replica` (`172.29.78.11`), все три Sentinel
указывают на него. После `docker start iot-redis` бывший основной узел вернулся репликой (у нового основного `connected_slaves:1`),
не став основным (R14). Не проверялось: длительность переключения и счётчик `device_cache_requests_total{result="error"}` в момент
отказа — замер времени и метрик не делался (на прототипе переключение занимало ≈7 с).

**T064 — побочная находка (статические адреса Redis).** Тест на чистом стенде воспроизвёл `Address already in use` у `redis-replica`:
Docker выдаёт динамические адреса контейнерам без `ipv4_address` с начала той же подсети, и при параллельном старте один из них занимал
адрес реплики. Исправлено: динамические адреса ограничены верхней половиной подсети (`ipam.config.ip_range`, переменная `IOT_NET_IP_RANGE`),
статические адреса Redis и Sentinel остаются в нижней. На стенде разработчика это не проявлялось из-за порядка запуска.
