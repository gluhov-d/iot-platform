# Feature Specification: device-service — управление устройствами

**Feature**: `001-device-service` | **Created**: 2026-11-11 | **Status**: На проверке дизайна
**Input**: администратор хочет открыть карточку устройства, исправить её, удалить устройство или завести новое
вручную (например, если событие от роутера не дошло). Нужен сервис с REST API для этого; писатель реестра
устройств остаётся один — device-collector-service.

Как это устроено — [plan.md](plan.md), [data-model.md](data-model.md), [контракт API](contracts/device-service.yaml),
[ADR](../../docs/adr/README.md); порядок реализации — [tasks.md](tasks.md); сценарий проверки на стенде —
[quickstart.md](quickstart.md).

## Clarifications

### Session 2026-11-11

- Q: Кто назначает `deviceId` при ручном создании? → A: клиент: это идентификатор физического устройства, тот же, что
  в событиях роутера ([ADR-0006](../../docs/adr/0006-device-id-assigned-by-client.md)).
- Q: Кто и когда сбрасывает кэш, если запись идёт через Kafka, а реплика отстаёт? → A: владелец данных
  (device-collector-service) после фиксации изменения; данные старее последней применённой версии в кэш не попадают
  ([ADR-0003](../../docs/adr/0003-cache-invalidation-by-owner.md)).
- Q: Как выполняется удаление и что будет, если после него придёт событие роутера? → A: удаление мягкое с отметкой
  «удалено администратором»; события роутера устройство не возвращают, вернуть можно только `POST`
  ([ADR-0005](../../docs/adr/0005-soft-delete-and-manual-priority.md)).
- Q: Как чтение попадает в реплики, а не в основные узлы шардов? → A: отдельная логическая база ShardingSphere-Proxy
  только из реплик; к базе записи у device-service доступа нет ([ADR-0004](../../docs/adr/0004-read-from-replicas.md)).
- Q: Что значит `operation = null`? → A: поле не заполнено — сообщение прежней версии схемы или событие роутера; оно
  применяется как раньше (для нового устройства это создание). Значение новее схемы читателя читается как `UNKNOWN`
  и отклоняется ([ADR-0002](../../docs/adr/0002-device-info-operation.md)).
- Q: Что меняет `PUT`? → A: целиком поля, которыми управляет администратор: имя, арендатор, владелец, тип, серийный
  номер, производитель, модель, статус, настройки, атрибуты. Прошивку, ОС, сенсоры и время активности сообщает
  устройство — в API они только для чтения.
- Q: Чья правка важнее: администратора или роутера? → A: после ручного изменения поля администратора меняют только
  команды; данные устройства роутер обновляет как раньше ([ADR-0005](../../docs/adr/0005-soft-delete-and-manual-priority.md)).
- Q: Как ответить на пользовательский токен? → A: `403 SERVICE_TOKEN_REQUIRED`
  ([ADR-0007](../../docs/adr/0007-service-tokens-only.md)).

### Session 2026-11-13

- Q: Тема `devices` сжимаемая (compact): после сжатия на ключ остаётся последнее сообщение, и повторное чтение темы
  при восстановлении из копии потеряло бы команду администратора, за которой пришло событие роутера. Что делать? →
  A: сообщения темы не сжимаются раньше заданного срока, копия шардов делается не реже этого срока; восстановление
  из более старой копии предупреждает о возможной потере ручных изменений
  ([ADR-0010](../../docs/adr/0010-devices-topic-compaction-lag.md)).
- Q: В реестре есть устройства без карточки (было только событие без данных устройства). Что отвечает `GET`? →
  A: `404`, как для отсутствующего: карточку заводит `POST` или первое событие с данными устройства.
- Q: Proxy при запуске подключается ко всем источникам и не стартует, если реплика недоступна — тогда встаёт и запись.
  Нужен ли отдельный Proxy для чтения? → A: нет, один Proxy с двумя базами; ограничение и порядок запуска —
  в [ADR-0004](../../docs/adr/0004-read-from-replicas.md).
- Q: Кто пишет код? → A: ИИ-агент по [tasks.md](tasks.md) (`implement`, затем `converge`); человек проверяет результат
  по задачам и выполняет необратимые шаги (правила — [AGENTS.md](../../AGENTS.md)).

## User Scenarios & Testing

### User Story 1 — Чтение карточки устройства (P1) 🎯 MVP

Сервис-потребитель запрашивает устройство по `deviceId` и получает его текущие данные.

**Independent Test**: `GET /api/v1/devices/{deviceId}` с сервисным токеном для устройства из реестра — `200`.

1. **Given** устройство есть в реестре, кэш пуст, **When** GET, **Then** `200`, данные взяты из реплики и сохранены в кэше.
2. **Given** устройство в кэше, **When** GET, **Then** `200` без обращения к базе.
3. **Given** устройства нет, оно удалено или у него нет карточки, **When** GET, **Then** `404 DEVICE_NOT_FOUND`.
4. **Given** Redis недоступен, **When** GET, **Then** `200` из реплики.

### User Story 2 — Изменение карточки (P1)

**Independent Test**: PUT → `202`; не позже чем через 5 с GET возвращает новые данные.

1. **Given** устройство есть, **When** PUT с валидным телом, **Then** `202`, в теме `devices` команда `UPDATE`.
2. **Given** устройства нет или оно удалено, **When** PUT, **Then** `404`, команд в теме нет.
3. **Given** тело не проходит проверку, **When** PUT, **Then** `400 VALIDATION_FAILED` со списком полей.
4. **Given** Kafka недоступна, **When** PUT, **Then** `503 COMMAND_NOT_ACCEPTED`; повтор запроса безопасен.

### User Story 3 — Ручное создание (P2)

1. **Given** устройства нет, **When** POST с `deviceId`, **Then** `202`, `Location: /api/v1/devices/{deviceId}`, команда `CREATE`.
2. **Given** устройство уже есть, **When** POST, **Then** `409 DEVICE_ALREADY_EXISTS`.
3. **Given** устройство удалено администратором, **When** POST, **Then** `202`, устройство снова читается.

### User Story 4 — Удаление (P2)

1. **Given** устройство есть, **When** DELETE, **Then** `202`, затем GET — `404`.
2. **Given** устройство удалено администратором, **When** приходит событие роутера, **Then** GET по-прежнему `404`.

### User Story 5 — Доступ только для сервисов (P1)

1. Нет токена; чужая подпись или издатель; срок истёк; нет аудитории `device-service` — `401 UNAUTHORIZED`.
2. Пользовательский токен, даже с ролью и аудиторией, — `403 SERVICE_TOKEN_REQUIRED`.
3. Сервисный токен без нужной роли — `403 FORBIDDEN`; с ролью — успех.

### Edge Cases

- Предварительная проверка записи идёт по модели чтения, которая может отставать. Если владелец данных решил иначе
  (например, `UPDATE` удалённого устройства), `202` уже отдан, а команда получает исход `IGNORED` — он виден в журнале
  обработки и метриках, а не в ответе клиенту.
- После сжатия темы `devices` первая команда могла исчезнуть: `UPDATE` неизвестного устройства создаёт его, `DELETE`
  неизвестного сохраняет отметку удаления.
- Реплика ещё не получила изменение: GET отдаёт её данные, но в кэш их не кладёт.
- Redis недоступен при сбросе кэша: обработка сообщения не останавливается, устаревание ограничено TTL.
- Повтор POST, PUT, DELETE после сетевого сбоя даёт то же состояние (повтор POST — `409` или то же устройство).
- Read-your-writes не гарантируется: сразу после `202` GET может вернуть прежние данные.

## Requirements

У каждого требования — проверка: что вызвать и что получить. Автоматические проверки и их файлы названы в tasks.md.

### API и запись

- **FR-001**: `POST /api/v1/devices`, `PUT` и `DELETE /api/v1/devices/{deviceId}` публикуют в тему `devices` сообщение
  `DeviceInfo` с `operation` = `CREATE`, `UPDATE`, `DELETE` и ключом `deviceId`; в базу сервис не пишет.
  *Проверка*: после каждого запроса в теме ровно одно новое сообщение с этим ключом и операцией.
- **FR-002**: Ответ `202 Accepted` с `Location` отдаётся только после подтверждения Kafka.
  *Проверка*: при остановленной Kafka ответ `503 COMMAND_NOT_ACCEPTED` не позже `DEVICE_COMMAND_SEND_TIMEOUT`, сообщений нет.
- **FR-003**: `GET /api/v1/devices/{deviceId}` читает по паттерну Cache-Aside: Redis, при промахе — реплики шардов.
  `404`, если устройства нет, оно удалено или у него нет карточки.
  *Проверка*: первый GET — `200` и запись в кэше со сроком жизни не больше `DEVICE_CACHE_TTL`; второй GET — `200`,
  счётчик попаданий кэша вырос, запросов к базе не было.
- **FR-004**: `deviceId` задаёт клиент: 1–128 символов без пробелов и `/`.
  *Проверка*: POST без `deviceId` или с `deviceId` из 129 символов — `400 VALIDATION_FAILED`, сообщений в теме нет.
- **FR-005**: Предварительные проверки: POST существующего — `409 DEVICE_ALREADY_EXISTS`; PUT и DELETE отсутствующего
  или удалённого — `404 DEVICE_NOT_FOUND`. *Проверка*: эти ответы получены, сообщений в теме нет.
- **FR-006**: Все ошибки, включая 401 и 403, — Problem Details (`application/problem+json`) с `code` и `traceId`.
  *Проверка*: у ответа каждого кода ошибки есть `type`, `title`, `status`, `code`, `traceId`; нет стека, SQL, имён классов.
- **FR-007**: Наружу отдаются только DTO из контракта. *Проверка*: тело `GET` содержит только поля схемы `DeviceResponse`
  (нет служебных полей реестра).
- **FR-008**: Сервис не хранит состояние между запросами; в Docker Compose работают два экземпляра.
  *Проверка*: оба экземпляра `healthy`; одинаковый GET к каждому даёт одинаковое тело; `Set-Cookie` в ответах нет.

### Безопасность

- **FR-009**: Принимаются только сервисные токены Keycloak (client credentials): проверяются подпись по ключам
  Keycloak, издатель, срок действия, аудитория `device-service`; чтение требует роль `devices.read`, запись — `devices.write`.
  *Проверка*: случаи User Story 5 дают указанные коды с настоящими токенами Keycloak.
- **FR-010**: Настройки realm лежат в репозитории и применяются при запуске: клиент `device-service`, клиент-потребитель
  с сервисной учётной записью. *Проверка*: на чистом стенде после `make up` токен, полученный по
  [quickstart.md](quickstart.md), принимается сервисом без ручной настройки Keycloak; секретов в файле realm нет.

### API First

- **FR-011**: Файл OpenAPI в репозитории — источник истины; при сборке из него генерируются DTO и интерфейс HTTP Service
  Client; контроллер реализует этот интерфейс. *Проверка*: сгенерированного кода в Git нет; в сервисе нет библиотек,
  собирающих спецификацию из аннотаций; контроллер объявлен как реализация сгенерированного интерфейса.
- **FR-012**: Интерфейс и DTO публикуются в Nexus библиотекой `device-service-client` с версией.
  *Проверка*: артефакт версии из контракта есть в Nexus; повторная публикация той же версии с другим содержимым
  отклоняется; тест вызывает запущенный сервис через интерфейс из библиотеки.

### Контракт сообщений и доработка сервисов

- **FR-013**: В `DeviceInfo` добавлено необязательное поле `operation` (`CREATE`, `UPDATE`, `DELETE`; значение новее
  схемы читателя — `UNKNOWN`) со значением по умолчанию `null`; совместимость FULL; новая версия avros опубликована
  в Nexus и зарегистрирована в Schema Registry. *Проверка*: `make avros-check` проходит; сообщение прежней версии
  читается новой схемой с `operation = null`, сообщение новой версии читается прежней схемой; последняя версия
  `devices-value` в Schema Registry содержит `operation`.
- **FR-014**: events-collector-service переходит на новую версию avros и `operation` не заполняет.
  *Проверка*: его сообщения в `devices` имеют `operation = null`; прежние проверки сервиса проходят.
- **FR-015**: device-collector-service переходит на новую версию avros и применяет сообщения по таблице. Обработка
  идемпотентна; более старое сообщение не перезаписывает более новое.

  | № | Сообщение | Состояние устройства | Результат |
  |---|---|---|---|
  | 1 | `CREATE` | нет / есть / удалено | карточка создана или заменены поля администратора, удаление снято — `APPLIED` |
  | 2 | `UPDATE` | нет | карточка создана — `APPLIED` |
  | 3 | `UPDATE` | есть | заменены поля администратора — `APPLIED` |
  | 4 | `UPDATE` | удалено | без изменений — `IGNORED` |
  | 5 | `DELETE` | есть / нет | устройство помечено удалённым администратором — `APPLIED` |
  | 6 | команда старее последней применённой команды | любое | без изменений — `STALE` |
  | 7 | событие роутера | удалено администратором | без изменений — `IGNORED` |
  | 8 | событие роутера | были ручные изменения | обновлены только данные устройства — `APPLIED` |
  | 9 | событие роутера | ручных изменений не было | как раньше |
  | 10 | повтор уже обработанного сообщения | любое | без изменений — `DUPLICATE` |
  | 11 | `UNKNOWN`; `CREATE` или `UPDATE` без данных устройства | любое | сообщение уходит в `devices-dlt`, следующие обрабатываются |

  *Проверка*: для каждой строки таблицы — автоматический тест с указанным результатом.
- **FR-016**: Удаление мягкое; после удаления администратором событие роутера устройство не возвращает, `POST` —
  возвращает. *Проверка*: сценарии User Story 4.2 и 3.3.
- **FR-017**: Время события роутера не делает команду администратора устаревшей.
  *Проверка*: команда применяется, даже если последнее событие роутера имеет более позднее время.
- **FR-018**: Кэш устройства сбрасывает device-collector-service после фиксации изменения; данные старее последней
  применённой версии в кэш не попадают. *Проверка*: после `202` на PUT прежние данные перестают отдаваться не позже
  чем через 5 с и больше не появляются; пока реплика отдаёт версию старее применённой, GET возвращает её данные,
  но записи в кэше не появляется.
- **FR-019**: Чтение при промахе кэша идёт только в реплики. *Проверка*: после серии GET на основных узлах шардов
  нет ни одной сессии пользователя чтения, на репликах — есть.
- **FR-020**: Redis общий для платформы, все сервисы подключаются через Sentinel; срок жизни кэша задаёт
  `DEVICE_CACHE_TTL`. *Проверка*: после остановки основного узла Redis сервисы продолжают работать без перезапуска.
- **FR-021**: Недоступный Redis не ломает ни чтение, ни обработку сообщений.
  *Проверка*: при остановленном Redis GET существующего устройства — `200`; сообщения `devices` применяются.
- **FR-022**: Сообщения темы `devices` не сжимаются раньше `KAFKA_DEVICES_MIN_COMPACTION_LAG_MS`; восстановление
  шардов из копии старше этого срока предупреждает о возможной потере ручных изменений.
  *Проверка*: настройка темы показывает это значение; восстановление из старой копии печатает предупреждение.

### Эксплуатация

- **FR-023**: Метрики через Micrometer; у events-collector-service, device-collector-service, device-service и
  PostgreSQL — своя панель Grafana. *Проверка*: все запросы панелей выполняются без ошибок; в метках нет `deviceId`.
- **FR-024**: Логи всех компонентов — JSON с `traceId`, собираются в Loki; один `traceId` проходит от HTTP-запроса
  в device-service через Kafka и device-collector-service до записи в PostgreSQL.
  *Проверка*: трасса одного PUT в Tempo содержит спаны обоих сервисов и запроса к базе; токенов и секретов в логах нет.
- **FR-025**: Docker Compose общий для платформы; у сервиса Dockerfile в два этапа (JDK → JRE); образы без `latest`;
  секретов в репозитории нет, все параметры — в `.env.example`; у каждого исходящего вызова есть тайм-аут; проверка
  живости не зависит от внешних систем. *Проверка*: `make up` на чистом стенде завершается успешно; поиск `:latest`
  и секретов по репозиторию пуст.
- **FR-026**: Unit-тесты логики device-service и изменений device-collector-service; интеграционные тесты на
  Testcontainers с PostgreSQL, Kafka, Redis и Keycloak, токены настоящие; покрытие строк не ниже 70 %.
  *Проверка*: `./gradlew check` проходит; есть тесты: без токена, пользовательский токен, попадание и промах кэша,
  публикация в Kafka для каждой операции, полный путь от PUT до изменённых данных при чтении.

### Key Entities

- **Карточка устройства** — поля администратора и данные устройства, версия записи, отметка удаления. Владелец —
  device-collector-service; device-service её только читает.
- **Команда** — сообщение `DeviceInfo` с `operation`, идентификатором команды, временем приёма и полями администратора.
- **Запись кэша** — готовый ответ, версия записи и наименьшая версия, которую разрешено кэшировать.

## Success Criteria

- **SC-001**: Изменение, принятое с `202`, видно при чтении не позже чем через 5 с.
- **SC-002**: Ни одного запроса device-service к основным узлам шардов.
- **SC-003**: При остановленном Redis 100 % чтений существующих устройств успешны.
- **SC-004**: Ни один запрос без действительного сервисного токена с нужной ролью не выполняется.

## Assumptions

- Клиенты — сервисы платформы (API-оркестратор и проверочный клиент); пользователи ходят через оркестратор.
- Учебный стенд: тысячи устройств, единицы запросов в секунду; нагрузочные испытания вне рамок.
- Между двумя командами администратора для одного устройства побеждает принятая позже; оптимистичной блокировки
  (ETag, If-Match) нет.
- Защита кэша от одновременного промаха, несуществующих ключей и массового истечения TTL, а также вторая версия API
  — дополнительные задачи, решаются после основного объёма.
- Предположения о сторонних компонентах перечислены в [research.md](research.md); каждое проверяется задачей до
  зависящего от него кода.
