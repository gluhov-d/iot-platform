# Research: failed-events

Решения о сторонних компонентах и механизмах. «Проверено» — выполнено при подготовке дизайна на одноразовых прототипах
(Java 25, Spring Boot 4.0.3, Kafka 4.2.0, Schema Registry 8.2.4, MinIO `pgsty/minio:RELEASE.2026-08-04T00-00-00Z`,
Mimir 3.2.6, Loki 3.1.1, Tempo 2.6.0, Alloy v1.4.2, ClickHouse 26.2.19, PostgreSQL 18.6); код прототипов в репозиторий не входит.
«Предположение» — не проверялось: первая задача соответствующего блока tasks.md проверяет его до зависящего кода; не
подтвердилось — агент останавливается, применяется запасной вариант, правятся plan.md и ADR, повторяется `analyze`.

## Результаты проверок на стенде

(Заполняются при реализации: T070 — всплеск и скорость процессора, T049 — наблюдаемость, T060 — копии, T078 — приёмка на macOS-хосте (arm64).)

### T070 — всплеск при остановленном Proxy (R20, FR-012, SC-001)

Стенд: macOS-хост (arm64), свой проект Compose `iot-p8`, базовый профиль, чистые тома; один экземпляр процессора, `max-poll-records: 1`.
`DEVICES_MAX_ATTEMPTS=3`, `DEVICES_RETRY_INTERVAL=1s`, `DEVICES_RETRY_MULTIPLIER=2.0`.

Порядок: остановлены `failed-events-processor` и `shardingsphere-proxy`; в `events` отправлено 100 валидных событий со снимком устройства
(за 3 с). Событие проходит приём (ClickHouse доступен), outbox публикует производное сообщение в `devices`, и ошибку даёт
device-collector-service: Proxy недоступен, попытки исчерпаны. Затем запущены Proxy и процессор.

| Показатель | Результат |
|---|---|
| Записей `STORAGE_UNAVAILABLE` в `failed-events` | 100 из 100 (источник `device-collector-service`, тема `devices`) |
| Объектов `device-collector-service/…/STORAGE_UNAVAILABLE/` после запуска процессора | 100 (было 0); число записей равно числу объектов (SC-001). Измерено при прежнем ключе объекта (префикс по сервису и коду); после перехода на единый ключ по записи `failed-events` (ADR-0014) те же объекты отбираются по метаданным `error-code`, число на стенде не перепроверялось |
| Время накопления 100 записей (Proxy остановлен) | 1521 с, около 15 с на сообщение: один потребитель обрабатывает `devices` по очереди, до отказа тратятся три попытки и сетевая ошибка |
| Время слива 100 объектов процессором | 6 с по времени записи объектов в MinIO (20:26:51–20:26:56 UTC): по секундам 19, 29, 34, затем 17 за две секунды и 1 объект в последней |
| Скорость процессора | 17–34 объекта/с на экземпляре (в среднем около 17/с, пик 34/с); среднее время `s3.put-object` 31 мс (3,10 с на 100 записей) |
| Метрика `failed_events_archived_total{outcome="created",error_code="STORAGE_UNAVAILABLE"}` | 100 |

Вывод по R20: скорость слива на два порядка выше скорости появления ошибок (0,07/с, её ограничивает device-collector-service), поэтому
`max-poll-records` остаётся равным 1, пакетная запись не нужна.

Не проверено: отставание группы на панели Grafana (профиль observability на этом прогоне не поднимался). Скорость по снижению
`kafka-consumer-groups --describe` в этом прогоне получилась заниженной (0,8/с) и не используется: опрос шёл раз в несколько секунд
через `docker compose exec` на загруженном хосте, а раздел без зафиксированного смещения выводится прочерком и в сумму не попал.
