# Feature Specification: router-manager — команды роутерам

**Feature**: `003-router-manager` | **Created**: 2026-11-28 | **Status**: На проверке дизайна
**Input**: платформе нужен сервис, который принимает от администратора (а дальше — от API-оркестратора) команды для
роутеров, хранит их в PostgreSQL и выдаёт роутерам по их запросу через gRPC. Сервис на Go; контракт — в новом проекте
`protos`, из которого генерируется код и сервиса, и эмулятора роутеров. Прочие сервисы не меняются; окружение платформы получает то, без чего сервис не
работает: `postgres` в базовом стенде, второй запуск db-migrator, клиенты realm, сбор метрик и логов Alloy, правило
оповещения Grafana (перечень — раздел router-manager в `docs/definition-of-done.md`).

Как это устроено — [plan.md](plan.md), [data-model.md](data-model.md), [контракт](contracts/router_manager.proto),
[ADR](../../docs/adr/README.md) (0020–0026); порядок реализации — [tasks.md](tasks.md); проверка на стенде —
[quickstart.md](quickstart.md); результаты прототипов — [research.md](research.md).

## Clarifications

### Session 2026-11-28

- Q: Какой тип вызова gRPC для получения команды и почему? → A: унарный `PollCommand` с интервалом опроса роутера. Задание
  задаёт опрос и негативный кэш, который имеет смысл только для опроса; унарный вызов балансируется по двум экземплярам на
  каждом вызове, легко ограничивается сроком и повторяется. Поток держит соединение на экземпляре и на миллионах роутеров
  означает миллионы открытых потоков; сравнение под нагрузкой — в необязательной части (FR-027,
  [ADR-0021](../../docs/adr/0021-command-issue-once.md)).
- Q: Что происходит, когда для роутера накопилось несколько команд? → A: выдаются по одной, в порядке создания (`created_at`,
  затем `command_id`). В ответе `more_pending = true`, если остались ещё команды в статусе NEW: роутер опрашивает сразу, не
  дожидаясь интервала. Порядок команд роутеру сохраняется, у каждой свой ответ (ADR-0021).
- Q: Как исключена ситуация «команда создана, а кэш продолжает отвечать, что её нет»? → A: создание сначала фиксирует
  команду в PostgreSQL, затем меняет поколение роутера в Redis и удаляет запись «нет команды». Опрос запоминает поколение до
  запроса в базу и записывает «нет команды» только если поколение за это время не изменилось — атомарно, скриптом Lua в Redis.
  Если Redis недоступен в момент создания, запись «нет команды» истекает сама: срок записи вместе со сроком вызова меньше
  двух интервалов опроса, поэтому при интервале 10 с третий опрос после создания уже идёт в базу
  ([ADR-0022](../../docs/adr/0022-negative-cache-with-generation.md), research.md R5).
- Q: Что если ответ с командой потерялся: статус уже SENT, а роутер команду не получил? → A: команда повторно не выдаётся —
  ни этому роутеру, ни другому. Через `ROUTER_COMMAND_SENT_TIMEOUT` её переводит в FAILED (`TIMEOUT`) проход зависших
  команд, срабатывает оповещение в Grafana, администратор решает, создавать ли новую. Повторная выдача REBOOT или
  UPDATE_AGENT роутеру, который команду на самом деле получил, хуже ложного FAILED
  ([ADR-0025](../../docs/adr/0025-stuck-commands-and-alert.md)).
- Q: Как сервис убеждается, что запрос пришёл от настоящего роутера, если роутеров миллионы? → A: у каждого роутера свой
  ключ, выведенный из мастер-ключа сервиса: `K_r = HMAC-SHA256(K_master, router_id)`; он записывается в роутер при
  производстве. Роутер подписывает имя метода, свой идентификатор, время, одноразовое значение (nonce) и поля тела
  (`command_id`, `outcome`, SHA-256 от `message`); сервис выводит ключ сам и сверяет подпись — без базы и Keycloak (менее
  микросекунды, research.md R17). Подменить итог в перехваченном запросе нельзя: подпись перестанет сходиться. Повтор
  закрывает одноразовость подписи: принятая подпись записывается в Redis `SET NX` на 120 с (вдвое больше окна ±60 с), второй
  такой же запрос — отказ (R23). Redis недоступен — проверка повтора пропускается и считается метрикой: опросы роутеров не
  останавливаются из-за Redis. Ротация — два мастер-ключа по идентификатору
  ([ADR-0023](../../docs/adr/0023-router-authentication-hmac.md)).
- Q: Где своя база router-manager? → A: база `iot_commands` на общем PostgreSQL платформы (она уже заложена в
  `POSTGRES_EXTRA_DBS`); сервис `postgres` переходит из профиля `platform` в базовый стенд; у сервиса своя роль
  `router_manager`. Шарды за ShardingSphere-Proxy не подходят: это реестр устройств, а сервис ходит в базу через pgx напрямую.
  Миграции — db-migrator, отдельным запуском со своим каталогом ([ADR-0026](../../docs/adr/0026-router-manager-database.md)).
- Q: Что с плановым Command Service на контейнерной схеме? → A: его заменяет router-manager. По прежнему плану команду
  доставлял сервис через Device Gateway, подтверждение шло через Kafka, тайм-аут вела Camunda. Задание задаёт обратную
  модель: роутер сам забирает команду и сообщает результат, зависшие команды переводит механизм сервиса. Связи Camunda и
  Device Gateway с командами со схемы убраны, сами узлы остаются как план ([ADR-0020](../../docs/adr/0020-router-manager-replaces-command-service.md)).
- Q: Откуда Go-код берёт `.proto`? → A: из артефакта `protos` в Nexus с явной версией, как Java-сервисы берут avros;
  транспортные структуры только сгенерированные, сгенерированный код в Git не попадает
  ([ADR-0024](../../docs/adr/0024-protos-project.md)).

## User Scenarios & Testing

### User Story 1 — Команда доходит до роутера и возвращается с результатом (P1) 🎯 MVP

Администратор создаёт команду, роутер получает её при очередном опросе, выполняет и сообщает результат; статус виден
администратору.

**Independent Test**: эмулятор с одним роутером и без отказов; `CreateCommand` REBOOT — не позже чем через три интервала
опроса `GetCommand` возвращает SUCCESS.

1. **Given** команда сохранена (ответ `CreateCommand` получен), **When** роутер опрашивает, **Then** получает команду, статус SENT.
2. **Given** команда SENT, **When** роутер сообщает успех, **Then** статус SUCCESS, `finished_at` заполнен.
3. **Given** команда SENT, **When** роутер сообщает отказ, **Then** статус FAILED, причина `ROUTER_FAILED`, текст роутера сохранён.
4. **Given** для роутера нет команд, **When** он опрашивает, **Then** ответ OK без команды.

### User Story 2 — Опросы миллионов роутеров не нагружают базу (P1)

1. **Given** роутер опросил и команды не было, **When** он опрашивает снова, **Then** ответ из Redis, запроса в базу нет.
2. **Given** создана команда, **When** роутер опрашивает с интервалом 10 с, **Then** получает её не позже третьего опроса.
3. **Given** Redis недоступен, **When** роутер опрашивает и администратор создаёт команды, **Then** всё работает через базу.

### User Story 3 — Ни одна команда не теряется молча и не выдаётся дважды (P1)

1. **Given** два экземпляра сервиса, **When** роутеры опрашивают оба, **Then** каждая команда выдана ровно один раз.
2. **Given** роутер получил команду и не ответил, **When** прошло `ROUTER_COMMAND_SENT_TIMEOUT`, **Then** статус FAILED
   (`TIMEOUT`) и в Grafana — оповещение по этой команде.
3. **Given** роутер ответил повторно или после TIMEOUT, **When** ответ пришёл, **Then** итоговый статус не меняется.

### User Story 4 — Только свои (P1)

1. **Given** нет токена или токен не того клиента, **When** вызывается метод администратора, **Then** отказ.
2. **Given** запрос роутера без подписи, с чужой подписью, старым временем, изменённым телом или повтор уже принятого,
   **When** он приходит, **Then** отказ.

### Edge Cases

- Ответ с командой потерялся: статус SENT, роутер команду не получил — повторно не выдаётся, через срок FAILED (`TIMEOUT`) и оповещение.
- Роутер ответил после TIMEOUT: статус остаётся FAILED (`TIMEOUT`), ответ `applied = false`; событие в логе и счётчик поздних ответов.
- Ответ по команде в статусе NEW (роутер её не получал) — `FAILED_PRECONDITION`; по чужой или несуществующей команде — `NOT_FOUND`
  (не раскрывает, что команда есть у другого роутера).
- `CreateCommand` повторён с тем же `request_id` для того же роутера (тайм-аут у вызывающего): возвращается уже созданная команда, вторая не создаётся.
- Redis недоступен в момент создания: команда сохранена, ответ OK; запись «нет команды» истекает сама (см. Clarifications).
- Срок вызова истёк, пока шёл запрос в базу: запрос прерывается, ответ `DEADLINE_EXCEEDED`; команда, уже переведённая в SENT, — как потерянный ответ.
- PostgreSQL недоступен: опрос из кэша «нет команды» отвечает, остальные вызовы — `UNAVAILABLE`; проход зависших пропускает такт.
- Keycloak недоступен при старте: сервис не стартует (без ключей он отверг бы все токены молча); после старта ключи в памяти, обновление — в фоне.
- Экземпляр остановлен посреди опроса: `GracefulStop` дожидается текущих вызовов в пределах `ROUTER_SHUTDOWN_TIMEOUT`.
- Часы роутера уходят больше чем на 60 с: запросы отвергаются (`UNAUTHENTICATED`), в логе причина `timestamp outside window`.

### Контракт protos

- **FR-001**: Проект `protos` в монорепозитории по образцу avros: все `.proto` платформы в `protos/proto/`, файл
  `iotplatform/router/v1/router_manager.proto` — дословно [contracts/router_manager.proto](contracts/router_manager.proto).
  Сборка проверяет `buf lint` (STANDARD) и совместимость с последним релизом в Nexus (`buf breaking`, правила `WIRE_JSON`) и
  публикует jar `com.github.gluhov.iotplatform:protos:<версия>` с файлами `.proto` и `buf.yaml` в `maven-releases`;
  выпущенная версия не перезаписывается. Первая версия — `1.0.0`.
  *Проверка*: `make protos-check` проходит; копия с удалённым полем без `reserved` и с переименованным значением enum —
  код ≠ 0 с текстом buf; после публикации (ЧЕЛОВЕК) `curl -sf $NEXUS/repository/maven-releases/com/github/gluhov/iotplatform/protos/1.0.0/protos-1.0.0.jar`
  — 200, повторная публикация той же версии отклоняется.
- **FR-002**: Go-код сервиса и эмулятора генерируется `buf generate` из `.proto` артефакта protos явной версии
  (`PROTOS_VERSION`), скачанного из Nexus; сгенерированный код в Git не попадает, транспортных структур, написанных вручную, нет.
  *Проверка*: `git ls-files services/router-manager | grep -c '\.pb\.go$'` = 0; `docker compose … build router-manager` собирает образ с пустого
  каталога `internal/gen`; `grep -rn 'type .*Request struct' services/router-manager --include=*.go | grep -v internal/gen` пусто.

### router-manager: методы

- **FR-003**: Наружу только gRPC (порт `ROUTER_MANAGER_GRPC_PORT`); HTTP только служебный на порту метрик: `/metrics`, `/health/live`,
  `/health/ready`, не публикуется на хост. Стандартная служба `grpc.health.v1.Health`; отражение gRPC — при
  `ROUTER_GRPC_REFLECTION=true` (стенд).
  *Проверка*: `docker compose port router-manager 9090` отдаёт адрес, порт метрик на хосте не опубликован; `grpcurl … list` показывает
  `iotplatform.router.v1.RouterAdminService`, `RouterAgentService`, `grpc.health.v1.Health`.
- **FR-004**: `CreateCommand`: проверка (`router_id` по шаблону data-model.md, тип не `UNSPECIFIED`, у `UPDATE_AGENT` непустой
  `params.version`, у REBOOT параметров нет) → `INVALID_ARGUMENT`; команда со статусом NEW сохраняется в PostgreSQL, ответ —
  только после фиксации; после фиксации поколение роутера в Redis меняется и запись «нет команды» удаляется; повтор с тем же
  `request_id` возвращает ту же команду.
  *Проверка*: unit — таблица проверок; IT — после ответа строка есть в базе, ключ `router:cmd:none:v1:{routerId}` удалён;
  два вызова с одним `request_id` — один `command_id`, одна строка.
- **FR-005**: `GetCommand` возвращает команду со статусом, причиной отказа, текстом роутера и временем создания, выдачи и
  завершения; нет такой — `NOT_FOUND`.
  *Проверка*: IT по всем четырём статусам.
- **FR-006**: `PollCommand` (роутер из проверенных метаданных): запись «нет команды» есть — ответ без команды без запроса в базу;
  иначе самая старая команда NEW роутера одним выражением переводится в SENT и возвращается; `more_pending` — есть ли ещё NEW;
  команды нет — запись «нет команды» с поколением (FR-012), ответ OK без поля `command`.
  *Проверка*: unit сервиса на заглушках; IT — три команды выдаются по порядку создания, у первых двух `more_pending = true`.
- **FR-007**: `ReportResult`: команда SENT этого роутера → SUCCESS или FAILED (`ROUTER_FAILED`, текст до 1024 символов),
  `applied = true`; итог уже есть — статус не меняется, `applied = false`, ответ с текущим статусом; команда NEW —
  `FAILED_PRECONDITION`; чужая или несуществующая — `NOT_FOUND`; `outcome = UNSPECIFIED` — `INVALID_ARGUMENT`.
  *Проверка*: unit переходов статусов (таблица data-model.md); IT — повторный ответ и ответ после TIMEOUT не меняют статус.

### router-manager: жизненный цикл и зависшие команды

- **FR-008**: Статусы NEW → SENT → SUCCESS | FAILED; переходы — только по таблице data-model.md; итоговые статусы не меняются.
  *Проверка*: unit — все пары «статус × событие».
- **FR-009**: Одна команда выдаётся ровно один раз, в том числе при двух экземплярах: выдача — одно выражение
  `UPDATE … WHERE command_id = (SELECT … FOR UPDATE SKIP LOCKED) RETURNING` (research.md R1). Потерянный ответ команду
  повторно не выдаёт.
  *Проверка*: IT — два экземпляра сервиса, эмулятор 50 роутеров, 1000 команд: каждая получена эмулятором один раз,
  в базе 1000 итоговых статусов.
- **FR-010**: Проход зависших в каждом экземпляре каждые `ROUTER_STUCK_SCAN_INTERVAL`: команды SENT старше
  `ROUTER_COMMAND_SENT_TIMEOUT` переводятся в FAILED (`TIMEOUT`) пачками до `ROUTER_STUCK_SCAN_BATCH` с `SKIP LOCKED`
  (research.md R2); на каждую — строка лога `event = command_stuck` с `command_id`, `router_id`, `command_type`, `sent_at` и
  `+1` к `router_manager_commands_stuck_total`.
  *Проверка*: unit прохода на заглушке часов и хранилища; IT — эмулятор с долей молчащих 1.0, срок 2 с: FAILED (`TIMEOUT`),
  ровно одна строка `command_stuck` на команду при двух экземплярах.
- **FR-011**: На каждую зависшую команду в Grafana срабатывает оповещение `RouterManagerCommandStuck` с меткой `command_id`:
  правило по Loki из research.md R18 (интервал 10 с), провижининг из репозитория; уведомления — в свой contact point
  (research.md R19).
  *Проверка*: `make rm-quick-check` создаёт команду молчащему роутеру эмулятора и ждёт экземпляр оповещения с её `command_id`
  в состоянии `Alerting` (`/api/prometheus/grafana/api/v1/alerts`) не дольше `ROUTER_COMMAND_SENT_TIMEOUT` + 60 с.

### Негативный кэш

- **FR-012**: Redis платформы (Sentinel): запись «нет команды» `router:cmd:none:v1:{routerId}` со сроком `ROUTER_NEG_CACHE_TTL`;
  поколение `router:cmd:gen:v1:{routerId}`; запись — только если поколение не изменилось с начала опроса (Lua), создание —
  `INCR` поколения и удаление записи (Lua) после фиксации. Ограничение `ROUTER_NEG_CACHE_TTL + ROUTER_REQUEST_TIMEOUT < 20 с`
  (два интервала по 10 с) проверяется при старте.
  *Проверка*: unit — гонка «создание между чтением базы и записью кэша» не оставляет записи; IT — повторный опрос без команды
  не выполняет ни одного SQL (счётчик запросов pgx); команда, созданная при недоступном Redis, получена не позже третьего опроса.
- **FR-013**: Redis недоступен — опрос и создание идут через базу, ответы штатные; ошибки Redis — в логе и в
  `router_manager_cache_errors_total`, клиент восстанавливается сам.
  *Проверка*: IT — `docker pause` Redis: опрос, создание, выдача, результат; после `unpause` повторный опрос снова из кэша.

### Ресурсы, сроки, хранение

- **FR-014**: Срок вызова передаётся до PostgreSQL и Redis: срок обработки — меньшее из срока клиента и `ROUTER_REQUEST_TIMEOUT`;
  pgx получает этот `context`, go-redis создан с `ContextTimeoutEnabled` (предположение research.md R7, проверяет T021).
  *Проверка*: IT — опрос с дедлайном 300 мс при приостановленном Redis и медленном запросе (`pg_sleep` в тестовой обёртке)
  возвращает `DEADLINE_EXCEEDED` не позже чем через 400 мс.
- **FR-015**: Своя база `iot_commands` на общем PostgreSQL, своя роль `router_manager` (только `SELECT, INSERT, UPDATE` на свои
  таблицы), доступ pgx без ORM и без ShardingSphere-Proxy. Схема — миграции db-migrator (`IF NOT EXISTS`) в
  `services/db-migrator/src/main/resources/db/migration/router-manager/`, отдельный одноразовый запуск `db-migrator-router-manager`.
  *Проверка*: `make up` с пустыми томами — таблица и индексы есть, `has_table_privilege('router_manager','router_commands','delete')` = false;
  повторный `make up` миграции не меняет.
- **FR-016**: Состояния в памяти нет: команды, статусы и кэш — только в PostgreSQL и Redis; в Compose два экземпляра
  (`deploy.replicas: 2`).
  *Проверка*: IT FR-009 с двумя экземплярами; остановка одного экземпляра посреди прогона эмулятора — команды доходят через второй.

### Безопасность

- **FR-017**: Методы администратора принимают только сервисный токен Keycloak, как device-service: подпись RS256 по ключам
  realm, `iss`, `exp`, аудитория `router-manager`, есть `client_id` и нет `sid`; роли клиента `router-manager`: `commands.write` —
  `CreateCommand`, `commands.read` — `GetCommand`. Нет токена, подпись, срок, издатель, аудитория → `UNAUTHENTICATED`;
  пользовательский токен или нет роли → `PERMISSION_DENIED`. В realm: клиент `router-manager` (роли),
  `router-manager-consumer` (обе роли), `router-manager-reader` (`commands.read`).
  *Проверка*: IT с Keycloak 26.0.8 — вызов без токена, с токеном `device-service-consumer` (чужая аудитория), `router-manager-reader`
  на `CreateCommand`, `router-manager-consumer`.
- **FR-018**: Методы роутера принимают только подписанные запросы (ADR-0023): метаданные `x-router-id`, `x-router-ts`,
  `x-router-nonce`, `x-router-key-id`, `x-router-sig`; подпись покрывает метод, роутер, время, nonce и поля тела (строка —
  data-model.md); ключ роутера выводится из мастер-ключа `ROUTER_AUTH_KEYS[key-id]`; окно `ROUTER_AUTH_MAX_SKEW`; принятая
  подпись одноразовая: `SET NX router:sig:v1:{routerId}:{sig}` на `ROUTER_AUTH_REPLAY_TTL`, уже есть — отказ; Redis недоступен —
  запрос принимается, `router_manager_replay_check_skipped_total` +1; отказ — `UNAUTHENTICATED` без подробностей, причина — в лог.
  *Проверка*: unit — таблица research.md R17 и подмена каждого поля тела; IT — эмулятор с неверным мастер-ключом, повтор
  принятого запроса и `ReportResult` с изменённым `outcome` получают `UNAUTHENTICATED`; при приостановленном Redis опрос
  проходит и счётчик растёт.
- **FR-019**: Ответы с ошибкой не раскрывают внутренности: код gRPC и короткий текст без SQL, стека и имён типов; паника
  обработчика — `INTERNAL`, сервис работает дальше.
  *Проверка*: unit перехватчика восстановления; IT — `GetCommand` с невалидным UUID — `INVALID_ARGUMENT` без текста pgx.

### Эмулятор роутеров

- **FR-020**: Эмулятор — программа на Go в том же модуле (`cmd/router-emulator`, пакет `emulator`), работает через сгенерированный
  клиент protos. Параметры (окружение): `EMULATOR_ROUTERS`, `EMULATOR_POLL_INTERVAL`, `EMULATOR_FAILURE_RATE`,
  `EMULATOR_SILENT_RATE`, `EMULATOR_EXEC_DELAY`, `EMULATOR_ROUTER_PREFIX`, `EMULATOR_TARGET`, `EMULATOR_METRICS_PORT`; опрос сразу при `more_pending`; молчащий роутер
  команду получает и не отвечает; свои метрики (опросы, полученные команды, ответы, задержка опроса).
  *Проверка*: unit пакета `emulator` на заглушке сервиса (доли отказов и молчания на 1000 командах — в пределах ±5 %); IT
  FR-009/FR-010/FR-012 используют эмулятор.

## Key Entities

- **Команда** (`router_commands`): идентификатор, роутер, тип, параметры, ключ идемпотентности, статус, причина отказа, текст
  роутера, время создания, выдачи, завершения, кто создал (`client_id`). Владелец — router-manager.
- **Запись «нет команды»** и **поколение роутера** — производные данные в Redis, источник истины — PostgreSQL.
- **Роутер** — только идентификатор и выведенный ключ; реестра роутеров в этой части нет.

## Success Criteria

- **SC-001**: Команда, созданная для роутера с интервалом опроса 10 с, выдаётся не позже третьего опроса — и при недоступном Redis.
- **SC-002**: Повторные опросы без команды не доходят до PostgreSQL (0 запросов на опрос с попаданием в кэш).
- **SC-003**: 1000 команд при двух экземплярах — 1000 выдач, ни одной двойной.
- **SC-004**: Каждая зависшая команда за `ROUTER_COMMAND_SENT_TIMEOUT` + 60 с становится FAILED (`TIMEOUT`) и даёт отдельный
  экземпляр оповещения с её `command_id`.
- **SC-005**: Ни одного метода администратора без сервисного токена с нужной ролью и ни одного метода роутера без верной подписи.

## Assumptions

- Ключи роутеров записываются при производстве; провижининг ключей и реестр роутеров — вне этой части. Эмулятор знает мастер-ключ
  стенда, чтобы вывести ключи своих роутеров.
- Внешний порт роутеров в продуктиве закрывается TLS на балансировщике; на стенде — открытый HTTP/2 внутри сети Compose.
- Часы роутеров синхронизированы (NTP) с точностью лучше 60 с.
- «Наружу только gRPC»: служебный HTTP-порт (`/metrics`, `/health/*`) открыт только внутри сети Compose для Alloy и
  проверок, на хост не публикуется.
