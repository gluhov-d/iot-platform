# IoT Platform Constitution

Правила для всех сервисов платформы. Каждый шаг Spec Kit (`plan`, `tasks`, `analyze`, `converge`) проверяется
на соответствие им; отступление записывается в Complexity Tracking плана с причиной.

## Core Principles

### I. Один владелец данных
У каждого набора данных один сервис-писатель, его хранилище — источник истины. Остальные копии (реплики, кэши,
витрины) производные и данные не меняют. Изменения к владельцу приходят событиями Kafka с ключом сущности,
поэтому записи одной сущности идут строго по очереди без блокировок между сервисами.

### II. Контракты первичны и меняются совместимо
- Avro-схемы живут только в `avros/`, публикуются в Nexus с явной версией и регистрируются в Schema Registry
  в режиме `FULL_TRANSITIVE`. Новое поле — необязательное, со значением по умолчанию; поля не удаляются
  и не переименовываются. Продюсеры не регистрируют схемы сами.
- HTTP API — API First: файл OpenAPI в репозитории и есть контракт; DTO и клиент генерируются при сборке,
  спецификация из аннотаций кода не принимается. Несовместимое изменение — новая версия пути (`/api/v2`).
- Изменения схемы БД — только миграциями `db-migrator`, обратно совместимые (`IF NOT EXISTS`).

### III. Обработка идемпотентна
Доставка — как минимум один раз. Повтор сообщения не меняет результат, более старое сообщение не перезаписывает
более новое. Ответ «принято» клиенту — только после подтверждения записи брокером или хранилищем.

### IV. Сервисы без состояния, конфигурация из окружения
Нет сессий, локальных файлов и общих данных в памяти экземпляра: всё общее — в PostgreSQL, Redis, Kafka.
Все адреса, тайм-ауты, TTL, число попыток, секреты — переменные окружения, перечисленные в `.env.example`;
секретов в репозитории нет. У каждого исходящего вызова есть тайм-аут.

### V. Безопасность по умолчанию
Сервис проверяет каждый запрос сам (нулевое доверие): подпись JWT по ключам Keycloak, издатель, срок, аудитория,
права. Настройки Keycloak (realm) лежат в репозитории и применяются при запуске. Ответ с ошибкой не раскрывает
внутренности: стек, SQL, имена классов.

### VI. Наблюдаемость обязательна
Метрики Micrometer (RED для сервиса, без меток с высокой кардинальностью вроде `deviceId`), логи в JSON
с `traceId`/`spanId` в Loki, трассы OpenTelemetry в Tempo с передачей контекста через HTTP и Kafka.
У каждого сервиса своя панель Grafana.

### VII. Тесты на настоящей инфраструктуре
Unit-тесты на логику без инфраструктуры; интеграционные — Testcontainers с теми же образами, что на стенде
(Kafka, Schema Registry, PostgreSQL, Redis, Keycloak). Безопасность проверяется с настоящими токенами Keycloak.
Порог покрытия строк — 70 %.

## Технологии и запуск

- Java 25, Spring Boot 4, Gradle (Kotlin DSL), монорепозиторий.
- Kafka 4 (KRaft) + Confluent Schema Registry, PostgreSQL за ShardingSphere-Proxy, ClickHouse, Redis через
  Sentinel, Keycloak, Nexus, Prometheus/Loki/Tempo/Grafana.
- Один Docker Compose на платформу; у сервиса свой Dockerfile в два этапа (JDK → JRE), образы и зависимости —
  с фиксированными версиями, без `latest`.
- Ошибки HTTP — Problem Details (RFC 9457) с `code` и `traceId`.

## Порядок работы

1. Дизайн через Spec Kit: `constitution` → `specify` → `clarify` → `plan` → `tasks` → `analyze`. Артефакты
   короткие: без повторов между spec, plan и tasks, у решения — причина, критерии приёмки проверяемые.
2. Ключевые решения — ADR в `docs/adr/`. Диаграммы — Mermaid в `diagrams/`.
3. Код — только после того, как дизайн принят. Реализация — `implement`, затем `converge` до `Converged`.

## Governance

Конституция важнее частных решений в spec и plan. Изменение — отдельным коммитом с новой версией и
перечнем затронутых артефактов.
